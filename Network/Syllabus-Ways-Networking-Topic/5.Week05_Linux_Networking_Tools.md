## 1. ip command

### Overview
`ip` হলো Linux-এর **swiss army knife** for networking — interfaces, routes, addresses, tunnels, ARP table — সব manage করে। `ifconfig`-এর modern replacement।

```bash
# ip কমান্ডের structure:
ip [ OPTIONS ] OBJECT { COMMAND | help }

# Main OBJECTs:
#   link     → Network interfaces (L2)
#   address  → IP addresses (L3)
#   route    → Routing table
#   neigh    → ARP/NDP table
#   netns    → Network namespaces
```

### ip link — Interface Management (L2)

```bash
# সব interface list
ip link show

# নির্দিষ্ট interface
ip link show eth0

# Interface up/down
sudo ip link set eth0 up
sudo ip link set eth0 down

# Interface rename
sudo ip link set eth0 name external-if

# MTU change
sudo ip link set eth0 mtu 9000

# MAC address change
sudo ip link set eth0 address 00:11:22:33:44:55

# Interface statistics
ip -s link show eth0
# RX: bytes  packets  errors  dropped  overrun  mcast
# TX: bytes  packets  errors  dropped  carrier  collsn
```

### ip address — IP Address Management (L3)

```bash
# সব IP address দেখো
ip addr show
ip a    # short form

# নির্দিষ্ট interface-র IP
ip addr show eth0

# IP address add
sudo ip addr add 192.168.1.100/24 dev eth0

# Multiple IPs on same interface (secondary/virtual IP)
sudo ip addr add 192.168.1.101/24 dev eth0

# IP address delete
sudo ip addr del 192.168.1.100/24 dev eth0

# Output understanding:
# eth0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 state UP
#   inet 192.168.1.5/24 brd 192.168.1.255 scope global eth0
#   └── L3 address ──┘  └── Broadcast ──┘
```

### ip route — Routing Table

```bash
# Routing table show
ip route show
ip r    # short form

# Default route add
sudo ip route add default via 192.168.1.1 dev eth0

# Specific network route
sudo ip route add 10.0.0.0/8 via 192.168.1.254 dev eth0

# Directly connected route
sudo ip route add 172.16.0.0/16 dev eth1

# Route delete
sudo ip route del 10.0.0.0/8

# Output understanding:
# default via 192.168.1.1 dev eth0 proto static
# └─ default gateway ─┘  └─ interface ─┘

# 192.168.1.0/24 dev eth0 proto kernel scope link src 192.168.1.5
# └── local subnet ──┘ └─── interface ─┘ └──── my IP ────┘
```

### ip neigh — ARP/Neighbor Table

```bash
# ARP table দেখো (IPv4)
ip neigh show

# Output:
# 192.168.1.1 dev eth0 lladdr 11:22:33:44:55:66 REACHABLE
# 192.168.1.10 dev eth0 lladdr aa:bb:cc:dd:ee:ff STALE

# States: REACHABLE, STALE, DELAY, PROBE, FAILED, INCOMPLETE

# Manual ARP entry add
sudo ip neigh add 192.168.1.50 lladdr 00:11:22:33:44:55 dev eth0

# Clear ARP cache
sudo ip neigh flush all
```

### Research Context
- `ip -s link show` → interface packet/error counters → network health baselining
- Kubernetes nodes-এ `ip route` → pod subnet routing debug
- `ip neigh` → ARP spoofing detection (unexpected MAC changes)
- CNI plugins `ip` command heavily use করে virtual interfaces manage করতে

## 2. ss (Socket Statistics)

### Overview
`ss` হলো `netstat`-এর modern, faster replacement — socket statistics দেখার tool। Active connections, listening ports — সব দেখায়।

```bash
# Basic usage
ss [options] [ FILTER ]
```

### Common Options

```bash
# সব socket দেখো (TCP + UDP + Unix)
ss -a        # all sockets
ss -l        # listening sockets
ss -t        # TCP only
ss -u        # UDP only
ss -n        # numeric (resolve না করে — faster)
ss -p        # process info (PID/name)
ss -s        # summary statistics
ss -e        # extended info
ss -m        # memory usage
ss -i        # internal TCP info (rtt, rto, cwnd, etc.)

# Common combinations:
ss -tln      # TCP + Listening + Numeric ports  ← সবচেয়ে useful
ss -tuan     # সব TCP/UDP sockets, numeric
ss -tnp      # TCP connections with process info
```

### Output Understanding

```bash
ss -tlnp

# State   Recv-Q Send-Q Local Addr:Port   Peer Addr:Port   Process
# LISTEN  0      128    0.0.0.0:22         0.0.0.0:*        sshd (pid=1234)
# LISTEN  0      128    0.0.0.0:6443       0.0.0.0:*        kube-apiserver
# LISTEN  0      128    127.0.0.1:2379     0.0.0.0:*        etcd

# Column meanings:
# Recv-Q:  Receive queue — data received but NOT yet read by application
# Send-Q:  Send queue — data sent but NOT yet acknowledged
# 0.0.0.0: Listening on ALL interfaces
# 127.0.0.1: Listening ONLY on loopback
```

### Socket States

```
LISTEN        : Server — waiting for incoming connection
ESTAB         : Connected (data transfer ongoing)
SYN-SENT      : Client sent SYN, waiting for SYN-ACK
SYN-RECV      : Server received SYN, sent SYN-ACK, waiting for ACK
TIME-WAIT     : 2×MSL wait after closing (graceful cleanup)
CLOSE-WAIT    : Remote side sent FIN, local side hasn't closed yet
FIN-WAIT-1/2  : Connection closing stages
CLOSED        : Fully closed

suspicious:   Many SYN-RECV → SYN flood attack?
              Many TIME-WAIT → high connection churn
              CLOSE-WAIT accumulating → application bug (not closing)
```

### Filtering Examples

```bash
# Specific port-এ listening
ss -tln sport = :6443

# Specific destination
ss -tn dst 10.0.0.5

# Specific source port range
ss -tn sport \> :1024

# Established connections count
ss -tn state established | wc -l

# Connection state summary
ss -s
# TCP: 45 (estab 12, closed 20, timewait 10, synrecv 3)
```

### Research Context — IMPORTANT
- **Connection tracking**: `ss -tn` → current connections snapshot → flow baseline
- **Port monitoring**: `ss -tlnp` → unexpected listening ports → backdoor indicator
- **State distribution**: SYN-RECV count spike → SYN flood attack
- **Kubernetes debugging**: kube-apiserver (6443), kubelet (10250), etcd (2379) — port check

## 3. ping

### Overview
`ping` ICMP Echo Request পাঠিয়ে network reachability check করে এবং RTT measure করে।

```bash
ping [options] destination
```

### Basic Usage

```bash
# Basic ping (continuous — Ctrl+C to stop)
ping google.com

# Count limited
ping -c 4 google.com

# Output:
# PING google.com (142.250.80.46) 56(84) bytes of data.
# 64 bytes from 142.250.80.46: icmp_seq=1 ttl=118 time=14.2 ms
# 64 bytes from 142.250.80.46: icmp_seq=2 ttl=118 time=14.5 ms
# 64 bytes from 142.250.80.46: icmp_seq=3 ttl=118 time=14.1 ms
# 64 bytes from 142.250.80.46: icmp_seq=4 ttl=118 time=14.3 ms
#
# --- google.com ping statistics ---
# 4 packets transmitted, 4 received, 0% packet loss, time 3004ms
# rtt min/avg/max/mdev = 14.1/14.3/14.5/0.2 ms
```

### Key Options

```bash
ping -c 10 google.com          # Send 10 packets
ping -i 0.2 google.com         # Interval 0.2 sec (default 1s) — flood test
ping -s 1000 google.com        # Packet size 1000 bytes
ping -W 2 google.com           # Timeout 2 seconds per reply
ping -f google.com             # Flood ping (DANGER — requires sudo)
ping -I eth0 google.com        # Specific interface
ping -t 5 google.com           # TTL set to 5
```

### Reading ping Output (Performance Analysis)

```
rtt min/avg/max/mdev = 14.1/14.3/14.5/0.2 ms

min  = 14.1 ms  → Best case latency
avg  = 14.3 ms  → Typical latency
max  = 14.5 ms  → Worst case latency (occasional spike)
mdev = 0.2 ms   → Standard deviation → LOW = stable; HIGH = jittery

0% packet loss   → Perfect connection ✓
5% packet loss   → Noticeable performance issue
50%+ packet loss → Major problem
```

### Research Context
- Ping sweep detection → attacker reconnaissance pattern
- ICMP disabled in many environments → `ping` block ≠ host down
- RTT time-series → latency baseline for ML models
- Packet loss from ping → simple network health feature

## 4. traceroute

### Overview
`traceroute` source থেকে destination-এ পৌঁছাতে **প্রতিটি hop** (intermediate router) identify করে এবং per-hop latency measure করে।

### How It Works

```
traceroute sends packets with increasing TTL:

TTL=1 → Router1 decrements to 0 → drops → sends ICMP "Time Exceeded" back
        → We learn: Hop 1 = Router1 IP + RTT

TTL=2 → Passes Router1, Router2 decrements to 0 → drops → ICMP "Time Exceeded"
        → We learn: Hop 2 = Router2 IP + RTT

TTL=3 → Reaches destination → Destination sends ICMP "Echo Reply" (or UDP port unreachable)
        → We learn: Hop 3 = Destination IP + RTT

Traceroute DONE ✓
```

### Basic Usage

```bash
# Basic
traceroute google.com

# Output:
# 1  _gateway (192.168.1.1)  1.201 ms  1.152 ms  1.098 ms
# 2  10.20.30.1              5.432 ms  5.221 ms  5.389 ms
# 3  203.0.113.5            12.876 ms 12.654 ms 12.710 ms
# 4  * * *                    ← Firewall blocks ICMP (timeout)
# 5  72.14.237.130          14.201 ms 14.102 ms 14.155 ms
# 6  google.com (142.250.80.46)  14.523 ms  14.401 ms  14.482 ms

# * * * = no response (packet filtered/timed out)
# 3 probes per hop → jitter estimation
```

### Key Options

```bash
traceroute -n google.com       # No DNS resolution (faster)
traceroute -m 15 google.com    # Max 15 hops
traceroute -w 2 google.com     # Wait 2 sec max per probe
traceroute -I google.com       # Use ICMP (instead of UDP)
traceroute -T google.com       # Use TCP SYN (bypass ICMP blocks)
traceroute -p 443 google.com   # Specific port
```

### Reading traceroute Output

```
Hop 1:  1.1 ms     → Local gateway (very close)
Hop 2:  5.4 ms     → ISP first router (nearby)
Hop 3:  12.8 ms    → ISP edge (city level)
Hop 4:  ***        → Blocked/filtered (anonymous hop)
Hop 5:  14.2 ms    → ISP backbone / peering
Hop 6:  14.5 ms    → Destination

Key insight:   1.1ms → 5.4ms = domestic ISP network
               5.4ms → 14.5ms = cross-country transit
               14.5ms total = reasonable international latency

If Hop 2 shows 150ms → routing anomaly / satellite link / misconfiguration
```

### Research Context
- Traceroute data → network topology mapping
- Hop count → simple feature for distance estimation
- Sudden new hops → route hijacking indicator
- Per-hop latency spike → pinpoint network bottleneck
- Kubernetes pod → external service traceroute → path analysis

## 5. dig (Domain Information Groper)

### Overview
`dig` হলো advanced DNS query tool — `nslookup`-এর থেকে অনেক বেশি powerful এবং detailed output দেয়।

```bash
dig [@server] [name] [type] [options]
```

### Basic Queries

```bash
# A record query (IPv4)
dig example.com

# Short output only
dig example.com +short
# 93.184.216.34

# Specific record type
dig example.com AAAA      # IPv6
dig example.com MX        # Mail server
dig example.com NS        # Nameserver
dig example.com TXT       # Text records (SPF, DKIM)
dig example.com CNAME     # Alias
dig example.com SOA       # Start of Authority
dig example.com ANY       # All records (often blocked now)

# Reverse lookup (IP → name)
dig -x 93.184.216.34

# Query specific DNS server
dig @8.8.8.8 example.com
dig @1.1.1.1 example.com
```

### dig Output Anatomy

```bash
dig example.com

;; ANSWER SECTION:
example.com.    3600    IN    A    93.184.216.34
               └─┬──┘                └─────┬────┘
               TTL (seconds)           IP address

# Key fields:
# TTL (3600s = 1 hour): কতক্ষণ cache করা যাবে
# Status: NOERROR (success)
#         NXDOMAIN (domain doesn't exist)
#         SERVFAIL (DNS server failure)
# Query time: DNS resolution-এ কত msec লাগলো
```

### Advanced dig

```bash
# Trace full DNS resolution path (Root → TLD → Authoritative)
dig example.com +trace

# Show only TTL
dig example.com +noall +answer +ttlid

# Query statistics only
dig example.com +stats

# Batch query (file থেকে)
dig -f domain_list.txt

# DNS SEC validation
dig example.com +dnssec
```

### Research Context — IMPORTANT
- **DNS tunneling detection**: `dig +trace` → verify legitimate resolution path
- **NXDOMAIN rate**: high = DGA malware activity
- **TTL analysis**: abnormally low TTL → fast-flux malware
- **Query time**: DNS latency baseline
- Kubernetes: `dig my-svc.my-ns.svc.cluster.local` → service discovery verification

## 6. nslookup

### Overview
`nslookup` — simpler DNS query tool, interactive mode support করে। `dig`-এর predecessor।

```bash
nslookup [options] [hostname] [server]
```

### Basic Usage

```bash
# Forward lookup
nslookup example.com
# Server:  8.8.8.8
# Address: 8.8.8.8#53
#
# Non-authoritative answer:
# Name:    example.com
# Address: 93.184.216.34

# Specific record type
nslookup -type=MX example.com
nslookup -type=NS example.com
nslookup -type=TXT example.com
nslookup -type=SOA example.com

# Query specific server
nslookup example.com 1.1.1.1
```

### Interactive Mode

```bash
nslookup
> server 8.8.8.8        # DNS server switch
> set type=A             # Record type set
> example.com
> set type=MX
> example.com
> set debug              # Verbose output
> example.com
> exit
```

### dig vs nslookup

```
Feature         dig                     nslookup
────────────────────────────────────────────────────
Output detail   Very detailed            Simple
Scripting       Excellent                Awkward
+short option   Yes                      No
+ trace         Yes (delegation path)    No
DNS SEC support Built-in                 Limited
Use preference  Modern standard         Legacy but still works
Recommendation: dig for research/debugging, nslookup for quick checks
```

## 7. curl (Client URL)

### Overview
`curl` — versatile data transfer tool. HTTP/HTTPS, FTP, SMTP, DNS, — practically all protocols support করে। API testing-এর primary tool।

```bash
curl [options] [URL]
```

### HTTP Methods

```bash
# GET (default)
curl https://api.example.com/users

# HEAD (headers only)
curl -I https://example.com

# POST (JSON data)
curl -X POST https://api.example.com/users \
  -H "Content-Type: application/json" \
  -d '{"name":"Ash","email":"a@b.com"}'

# PUT
curl -X PUT https://api.example.com/users/1 \
  -H "Content-Type: application/json" \
  -d '{"name":"Updated Name"}'

# DELETE
curl -X DELETE https://api.example.com/users/1
```

### Essential Options

```bash
# Verbose — দেখো কী হচ্ছে (headers, TLS handshake, cert, etc.)
curl -v https://example.com

# Include response headers in output
curl -i https://example.com

# Output to file
curl -o output.html https://example.com
curl -O https://example.com/file.zip   # Original filename

# Follow redirects
curl -L https://bit.ly/shorturl

# Custom headers
curl -H "Authorization: Bearer token123" \
     -H "Accept: application/json" \
     https://api.example.com/data

# Authentication
curl -u username:password https://api.example.com
curl -H "Authorization: Bearer $(cat token.txt)" https://api.example.com

# Insecure mode (skip TLS verification — testing only!)
curl -k https://self-signed.example.com

# Time measurements (research gold!)
curl -w "@curl-format.txt" -o /dev/null -s https://example.com

# curl-format.txt content:
#     time_namelookup:  %{time_namelookup}\n
#     time_connect:     %{time_connect}\n
#     time_appconnect:  %{time_appconnect}\n
#     time_pretransfer: %{time_pretransfer}\n
#     time_starttransfer: %{time_starttransfer}\n
#     time_total:       %{time_total}\n
```

### Timing Breakdown (Research Feature!)

```
time_namelookup:    DNS resolution time
time_connect:       TCP 3-way handshake time
time_appconnect:    TLS handshake time (HTTPS only)
time_pretransfer:   Time until data transfer starts
time_starttransfer: Time until first byte received (TTFB)
time_total:         Total operation time

TLS overhead = time_appconnect - time_connect
Server processing = time_starttransfer - time_pretransfer
Data transfer = time_total - time_starttransfer
```

### Kubernetes-Related

```bash
# Check kube-apiserver health
curl -k https://k8s-master:6443/healthz

# Access service via ClusterIP
curl http://10.96.0.10:80

# Test Ingress
curl -H "Host: app.example.com" http://192.168.1.100

# Access pod directly
curl http://10.244.1.5:8080

# With service account token
curl -H "Authorization: Bearer $(cat /var/run/secrets/kubernetes.io/serviceaccount/token)" \
     -k https://kubernetes.default.svc/api/v1/namespaces
```

### Research Context
- API call timing breakdown → latency bottleneck identification
- HTTP header fingerprinting → client/tool identification
- TLS timing → certificate validation overhead
- Kubernetes API interaction debugging

## 8. wget

### Overview
`wget` — file downloader, recursive download + mirroring-এ specialized। `curl`-এর থেকে heavy-duty downloading-এ বেশি capable।

```bash
wget [options] [URL]
```

### Common Usage

```bash
# Basic download
wget https://example.com/file.zip

# Download with custom name
wget -O myfile.zip https://example.com/file.zip

# Resume interrupted download
wget -c https://example.com/large-file.iso

# Background download + log
wget -b -o download.log https://example.com/large-file.iso

# Recursive download (mirror website)
wget -r https://example.com/

# Mirror mode (complete website copy)
wget -m https://example.com/

# Limit speed (research = simulate network conditions)
wget --limit-rate=100k https://example.com/file.zip

# Retry on failure
wget --tries=5 https://unstable-server.com/file.zip
```

### curl vs wget

```
Feature           curl                    wget
────────────────────────────────────────────────────
Protocols         HTTP, FTP, SMTP, IMAP,  HTTP, HTTPS, FTP
                  LDAP, SCP, SFTP, etc.
Recursive         Manual loop needed      Built-in (-r, -m)
Resume            -C -                     -c
API testing       Excellent                Not suitable
Pipe output       Yes (default stdout)     Needs -O -
Library           libcurl                  N/A (standalone)
Install base      Almost always present     Often needs install
```
