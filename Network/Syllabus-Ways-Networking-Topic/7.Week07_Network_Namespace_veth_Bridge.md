## 1. Network Namespace

### সংজ্ঞা
Network Namespace হলো Linux kernel feature যা সম্পূর্ণ **isolated network stack** create করে। প্রতিটি namespace-এর নিজস্ব interfaces, routes, iptables rules, ARP table থাকে।

```
Host (Default Namespace)              Namespace A            Namespace B
┌──────────────────────┐    ┌──────────────────────┐ ┌──────────────────────┐
│ eth0: 192.168.1.5    │    │ lo: 127.0.0.1         │ │ lo: 127.0.0.1        │
│ lo: 127.0.0.1        │    │ veth-a: 10.0.0.1      │ │ veth-b: 10.0.0.2     │
│                       │    │                       │ │                       │
│ Routes:               │    │ Routes:               │ │ Routes:               │
│ default via 192.168.1.1│   │ default via 10.0.0.254│ │ default via 10.0.0.254│
│                       │    │                       │ │                       │
│ iptables rules        │    │ Own iptables rules    │ │ Own iptables rules    │
│ ARP cache             │    │ Own ARP cache         │ │ Own ARP cache         │
└──────────────────────┘    └──────────────────────┘ └──────────────────────┘
   Complete isolation — namespace A knows nothing about namespace B
```

### Analogy
```
Network Namespace = আলাদা আলাদা apartment

একটা building (Linux host)-এর ভিতরে:
  - Apartment A: নিজস্ব door, নিজস্ব address, নিজস্ব lock
  - Apartment B: নিজস্ব door, নিজস্ব address, নিজস্ব lock

Apartment A-র মানুষ Apartment B-র ভিতরে দেখতে পায় না।
Communicate করতে চাইলে hallway (bridge) বা intercom (veth pair) দরকার।

Container = Network Namespace + Process Namespace + Mount Namespace + ...
```

### Namespace Commands

```bash
# সব network namespace list
ip netns list

# Namespace create
sudo ip netns add ns1
sudo ip netns add ns2

# Namespace-এ command execute
sudo ip netns exec ns1 bash          # Enter namespace shell
sudo ip netns exec ns1 ip addr show  # Single command
sudo ip netns exec ns1 ping 8.8.8.8

# Namespace delete
sudo ip netns delete ns1

# Inspect namespace
ls -la /var/run/netns/               # Persistent namespace locations
```

### Namespace-এর ভিতরে কী থাকে?

```bash
# Create namespace and explore
sudo ip netns add demo
sudo ip netns exec demo bash

# Inside namespace:
ip addr show
# 1: lo: <LOOPBACK> mtu 65536 state DOWN
# (শুধু loopback — অন্য কিছু নেই!)

ip route show
# (empty — কোনো route নেই)

iptables -L
# (empty — কোনো firewall rule নেই)

# Everything is isolated!
exit
```

### Practical: Two Namespaces with veth

```bash
# Create namespaces
sudo ip netns add red
sudo ip netns add blue

# Verify
ip netns list

# Red namespace-এ loopback up
sudo ip netns exec red ip link set lo up
sudo ip netns exec blue ip link set lo up

# Check — red can only see loopback
sudo ip netns exec red ip addr show
```

### Research Context — CRITICAL
```
Container = Network Namespace:
  Docker container → own network namespace
  Kubernetes Pod → shared network namespace (all containers in pod)

Why this matters for your research:
  1. Pod-to-Pod communication = Namespace-to-Namespace
  2. CNI plugins = namespace setup automation
  3. Network Policy = namespace traffic filtering
  4. Flow collection = per-namespace interface monitoring

Key insight: Kubernetes networking = Linux network namespaces + veth + bridge
              at scale, managed by CNI plugins
```

## 2. veth Pair (Virtual Ethernet Pair)

### সংজ্ঞা
veth pair হলো **virtual cable** — দুটি virtual interface的一端-to-一端 connected। এক প্রান্তে যা send হয়,另一端-এ receive হয়।

```
┌──────────────┐         ┌──────────────┐
│  veth-red    │◄══════►│  veth-blue   │
│  (end A)     │ virtual │  (end B)     │
└──────┬───────┘  cable  └──────┬───────┘
       │                        │
       ▼                        ▼
   Namespace                 Namespace
      Red                      Blue

Analogy: veth pair = pipe / walkie-talkie
         এক প্রান্তে কথা বললে另一端-এ শোনা যায়
```

### veth Pair Commands

```bash
# Create veth pair
sudo ip link add veth-red type veth peer name veth-blue

# Both ends in default namespace
ip link show | grep veth
# veth-red@veth-blue: ...
# veth-blue@veth-red: ...

# Move one end to a namespace
sudo ip link set veth-red netns red
sudo ip link set veth-blue netns blue

# Now each namespace has one end
sudo ip netns exec red ip link show
sudo ip netns exec blue ip link show

# Assign IP and bring up
sudo ip netns exec red ip addr add 10.0.0.1/24 dev veth-red
sudo ip netns exec red ip link set veth-red up

sudo ip netns exec blue ip addr add 10.0.0.2/24 dev veth-blue
sudo ip netns exec blue ip link set veth-blue up

# Now they can ping each other!
sudo ip netns exec red ping 10.0.0.2
# 64 bytes from 10.0.0.2: icmp_seq=1 ttl=64 time=0.050 ms ✓
```

### Complete veth Pair Lab

```bash
#!/bin/bash
# Create two isolated namespaces and connect them

# 1. Create namespaces
sudo ip netns add ns-client
sudo ip netns add ns-server

# 2. Create veth pair
sudo ip link add veth-client type veth peer name veth-server

# 3. Assign ends to namespaces
sudo ip link set veth-client netns ns-client
sudo ip link set veth-server netns ns-server

# 4. Configure IPs
sudo ip netns exec ns-client ip addr add 192.168.100.1/24 dev veth-client
sudo ip netns exec ns-server ip addr add 192.168.100.2/24 dev veth-server

# 5. Bring up interfaces + loopback
sudo ip netns exec ns-client ip link set veth-client up
sudo ip netns exec ns-client ip link set lo up
sudo ip netns exec ns-server ip link set veth-server up
sudo ip netns exec ns-server ip link set lo up

# 6. Test
sudo ip netns exec ns-client ping -c 3 192.168.100.2
# SUCCESS ✓

# 7. Check ARP
sudo ip netns exec ns-client ip neigh show
# 192.168.100.2 dev veth-client lladdr ... REACHABLE
```

### Kubernetes Context

```
Pod Network = veth pair:

Host (root namespace)                Pod (namespace)
┌─────────────────────┐             ┌──────────────────┐
│                     │             │                  │
│  veth-abc123@eth0   │◄══════════►│  eth0@veth-abc123│
│  (host end)         │  veth pair  │  (pod end)       │
│                     │             │  10.244.1.5/32   │
│  ┌────────────────┐ │             │                  │
│  │   cni0 bridge  │ │             └──────────────────┘
│  └────────┬───────┘ │
│           │          │
│    (to other pods)   │
└─────────────────────┘

প্রতিটি Pod-এর একটি veth pair:
  - Pod end: pod namespace-এ eth0 হিসেবে show করে
  - Host end: root namespace-এ vethXXXXXXXX হিসেবে show করে
  - Host end bridge (cni0/cbr0)-তে plugin হয়

Check on Kubernetes node:
  ip link show | grep veth    → সব pod veth দেখাবে
```

## 3. Bridge

### সংজ্ঞা
Linux Bridge হলো **virtual L2 switch** — একাধিক interface-কে একসাথে connect করে, same broadcast domain create করে। Physical switch-এর software version।

```
Without Bridge (isolated):          With Bridge (connected):
                                         ┌──────────────────┐
  NS1 ────  NS2 (no path)               │  BRIDGE (br0)    │
  NS1 ────  NS3 (no path)               │  10.0.0.254      │
  NS2 ────  NS3 (no path)               └──┬───────┬───────┘
                                         │       │
                                    ┌────▼──┐ ┌──▼──────┐
                                    │  NS1  │ │  NS2    │
                                    │10.0.0.1│ │10.0.0.2 │
                                    └───────┘ └─────────┘
                                    All connected via bridge!
```

### Bridge Commands

```bash
# Create bridge
sudo ip link add name br0 type bridge

# Bridge up
sudo ip link set br0 up

# Assign IP to bridge (host side)
sudo ip addr add 10.0.0.254/24 dev br0

# Add interfaces to bridge
sudo ip link set veth-red master br0    # veth-red → bridge member
sudo ip link set veth-blue master br0

# Show bridge and members
bridge link show
# or
ip link show type bridge
ip link show master br0

# Show bridge forwarding table (MAC learning)
bridge fdb show br br0
# MAC address → port mapping (like switch MAC table)
```

### Complete Bridge Lab

```bash
#!/bin/bash
# Multi-namespace network with bridge

# 1. Create bridge
sudo ip link add name br0 type bridge
sudo ip link set br0 up
sudo ip addr add 10.0.0.254/24 dev br0

# 2. Create 3 namespaces
sudo ip netns add ns1
sudo ip netns add ns2
sudo ip netns add ns3

# 3. Create veth pairs (1 per namespace)
sudo ip link add veth1 type veth peer name veth1-br
sudo ip link add veth2 type veth peer name veth2-br
sudo ip link add veth3 type veth peer name veth3-br

# 4. Assign veth ends
sudo ip link set veth1 netns ns1
sudo ip link set veth2 netns ns2
sudo ip link set veth3 netns ns3

# 5. Connect host-ends to bridge
sudo ip link set veth1-br master br0
sudo ip link set veth2-br master br0
sudo ip link set veth3-br master br0

# 6. Configure namespace IPs
sudo ip netns exec ns1 ip addr add 10.0.0.1/24 dev veth1
sudo ip netns exec ns2 ip addr add 10.0.0.2/24 dev veth2
sudo ip netns exec ns3 ip addr add 10.0.0.3/24 dev veth3

# 7. Bring everything up
sudo ip netns exec ns1 ip link set veth1 up
sudo ip netns exec ns1 ip link set lo up
sudo ip netns exec ns2 ip link set veth2 up
sudo ip netns exec ns2 ip link set lo up
sudo ip netns exec ns3 ip link set veth3 up
sudo ip netns exec ns3 ip link set lo up
sudo ip link set veth1-br up
sudo ip link set veth2-br up
sudo ip link set veth3-br up

# 8. Test connectivity
sudo ip netns exec ns1 ping -c 2 10.0.0.2   # ns1 → ns2 ✓
sudo ip netns exec ns2 ping -c 2 10.0.0.3   # ns2 → ns3 ✓
sudo ip netns exec ns3 ping -c 2 10.0.0.1   # ns3 → ns1 ✓

# 9. Each namespace can also ping the bridge!
sudo ip netns exec ns1 ping -c 2 10.0.0.254

# 10. Check bridge MAC learning
bridge fdb show br br0
# Shows which MAC is reachable via which port
```

### Bridge + External Access (Gateway)

```bash
# Add default route in namespaces → bridge as gateway
sudo ip netns exec ns1 ip route add default via 10.0.0.254
sudo ip netns exec ns2 ip route add default via 10.0.0.254
sudo ip netns exec ns3 ip route add default via 10.0.0.254

# Enable NAT on host for bridge network
sudo iptables -t nat -A POSTROUTING -s 10.0.0.0/24 -o eth0 -j MASQUERADE
sudo sysctl -w net.ipv4.ip_forward=1

# Now namespaces can reach internet!
sudo ip netns exec ns1 ping 8.8.8.8
# ✓ Internet access via bridge → host NAT
```

### Kubernetes Context

```
Docker/Kubernetes bridge model:

  ┌─────────────────────────────────────────────┐
  │                  HOST                        │
  │                                              │
  │   ┌──────────────────────────┐               │
  │   │    cni0 / cbr0 (bridge)  │  10.244.0.1   │
  │   └──┬─────────┬─────────┬──┘               │
  │      │         │         │                    │
  │   ┌──▼──┐   ┌──▼──┐   ┌──▼──┐               │
  │   │veth1│   │veth2│   │veth3│  (host end)    │
  │   └──┬──┘   └──┬──┘   └──┬──┘               │
  └──────┼─────────┼─────────┼───────────────────┘
         │         │         │
    ┌────▼──┐ ┌───▼───┐ ┌───▼───┐
    │ Pod 1 │ │ Pod 2 │ │ Pod 3 │
    │eth0   │ │eth0   │ │eth0   │   (pod end)
    │10.244 │ │10.244 │ │10.244 │
    │ .1.2  │ │ .1.3  │ │ .1.4  │
    └───────┘ └───────┘ └───────┘

cni0 bridge = Pod network backbone
veth pairs = each pod's virtual cable to bridge
```

## 4. Virtual Interface

### সংজ্ঞা
Virtual Interface হলো **software-defined** network interface, physical hardware না থেকেও network interface-এর মতো আচরণ করে।

### Types of Virtual Interfaces

```
┌──────────────────────────────────────────────────────────────────┐
│                    VIRTUAL INTERFACE TYPES                        │
├─────────────┬────────────────────────────────────────────────────┤
│ lo          │ Loopback — self communication (127.0.0.1)          │
│ dummy       │ Dummy — always up, no real traffic (placeholder)   │
│ veth        │ Virtual Ethernet — pair (container networking)     │
│ bridge      │ Virtual L2 switch — connects multiple interfaces    │
│ bond        │ Bonding — link aggregation (multiple NICs → one)    │
│ team        │ Team — alternative to bonding                      │
│ vlan        │ VLAN sub-interface — tagged traffic on one NIC      │
│ vxlan       │ VXLAN tunnel — L2 over L3 (Kubernetes overlay)      │
│ ipip        │ IP-in-IP tunnel                                     │
│ gre         │ GRE tunnel                                          │
│ tun         │ TUN — L3 tunnel (IP packets)                       │
│ tap         │ TAP — L2 tunnel (Ethernet frames)                  │
│ macvlan     │ Multiple MACs on one physical NIC                   │
│ ipvlan      │ Multiple IPs on same MAC                            │
│ wireguard   │ VPN interface                                       │
└─────────────┴────────────────────────────────────────────────────┘
```

### Key Virtual Interfaces for Research

#### 1. dummy Interface (Always-up placeholder)
```bash
sudo ip link add dummy0 type dummy
sudo ip addr add 10.99.99.1/24 dev dummy0
sudo ip link set dummy0 up

# Always stays UP — useful for testing, placeholder IP
```

#### 2. VLAN Interface (Tagged traffic)
```bash
# VLAN 10 on eth0 → eth0.10
sudo ip link add link eth0 name eth0.10 type vlan id 10
sudo ip addr add 192.168.10.1/24 dev eth0.10
sudo ip link set eth0.10 up

# Traffic to eth0.10 gets VLAN tag 10
```

#### 3. VXLAN Interface (Overlay — Kubernetes!)
```bash
# Create VXLAN tunnel
sudo ip link add vxlan0 type vxlan id 42 dev eth0 dstport 4789
sudo ip addr add 10.244.0.1/24 dev vxlan0
sudo ip link set vxlan0 up

# VXLAN ID 42, encapsulated in UDP port 4789, physical interface eth0
```

#### 4. macvlan Interface (Container direct to LAN)
```bash
# macvlan — container gets its own MAC, appears directly on LAN
sudo ip link add macvlan0 link eth0 type macvlan mode bridge
sudo ip addr add 192.168.1.200/24 dev macvlan0
sudo ip link set macvlan0 up

# macvlan0 appears as separate device on physical network
```

#### 5. TUN/TAP (VPN + VM networking)
```
TUN (L3):  Carries IP packets (routed VPN)
TAP (L2):  Carries Ethernet frames (bridged VPN)

Used by:  OpenVPN, WireGuard, QEMU/KVM, virtual machines
```

### Kubernetes-Relevant Virtual Interfaces

```bash
# On a Kubernetes node, you'll typically see:

ip link show

# lo:          Loopback
# eth0:        Physical NIC (node IP)
# cni0:        Bridge (pod network)
# flannel.1:   VXLAN tunnel (Flannel CNI)
# caliXXXX:    veth pair for Calico (one per pod)
# vethXXXX:    veth pair host-end (one per pod)
# kube-ipvs0:  Dummy for IPVS (kube-proxy IPVS mode)
# tunl0:       IPIP tunnel
```

### Research Context

```
1. Interface Monitoring:
   ip -s link → packet/error counters per interface
   → Dataset: per-interface statistics time-series

2. Container Interface Discovery:
   ls /sys/class/net/ → all interfaces (physical + virtual)
   → Identify pod interfaces vs host interfaces

3. Traffic Isolation:
   Which pod's veth is connected to which network?
   → Network Policy violation detection

4. CNI Debugging:
   Understanding veth/bridge/VXLAN → CNI troubleshooting
   Calico, Cilium, Flannel — all use these primitives

5. eBPF Attachment Points:
   eBPF programs can attach to:
     - veth interfaces (pod ingress/egress)
     - bridge (all pod traffic)
     - Physical NIC (node-level)
```
