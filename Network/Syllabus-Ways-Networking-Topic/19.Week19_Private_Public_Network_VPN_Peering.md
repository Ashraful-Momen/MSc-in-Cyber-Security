## 1. Private vs Public Network

```
PUBLIC NETWORK:
  - Internet-routable IPs
  - Accessible from anywhere
  - No privacy guarantee
  - Use: Web servers, APIs, CDNs

PRIVATE NETWORK:
  - RFC 1918 IPs (10.x, 172.16-31.x, 192.168.x)
  - NOT internet-routable
  - Isolated by default
  - Use: Databases, internal services, Kubernetes nodes

┌─────────────────────────────────────────────────────────────┐
│                  HYBRID NETWORK DESIGN                      │
│                                                             │
│  Internet ──► IGW ──► Public Subnet ──► Web Servers       │
│                          │                                  │
│                     NAT Gateway                              │
│                          │                                  │
│                          ▼                                  │
│                     Private Subnet ──► App Servers          │
│                          │                                  │
│                          ▼                                  │
│                     Private Subnet ──► Databases            │
│                                                             │
│  Layers of isolation:                                      │
│  - Different subnets (CIDR separation)                     │
│  - Different route tables (public vs private)              │
│  - Security Groups (service-level access)                  │
│  - NACL (subnet-level blocking)                            │
└─────────────────────────────────────────────────────────────┘
```

## 2. VPN (Virtual Private Network)

### VPN Types

```
1. Site-to-Site VPN:
   ┌──────────────┐         ┌──────────────┐
   │  Office Net  │◄─VPN──►│  Cloud VPC   │
   │  10.1.0.0/16 │  tunnel │  10.0.0.0/16 │
   └──────────────┘         └──────────────┘
   Two networks connected as one (encrypted tunnel over internet)

2. Client VPN:
   Laptop ──VPN──► Office/Cloud Network
   Single device connects to private network remotely

3. Direct Connect / ExpressRoute:
   ┌──────────────┐         ┌──────────────┐
   │  Office Net  │◄─Dedicated Fiber──►│  Cloud VPC   │
   └──────────────┘         └──────────────┘
   Private, dedicated physical connection — no internet
```

### IPSec VPN Components

```
IPSec Tunnel:
  ┌──────────────────────────────────────────────────────────┐
  │                                                          │
  │  Customer Gateway ◄════ IPSec Tunnel ════► VPN Gateway  │
  │  (Office Router)         (Encrypted)       (Cloud Side) │
  │                                                          │
  │  IKE Phase 1: Authenticate + establish secure channel    │
  │  IKE Phase 2: Negotiate IPSec SA for data transfer       │
  │                                                          │
  │  Encryption: AES-256                                     │
  │  Authentication: SHA-256                                 │
  │  Key Exchange: DH Group 14+                              │
  └──────────────────────────────────────────────────────────┘

Two tunnels per VPN connection (HA)
  Active/Passive or Active/Active (with BGP)
```

## 3. VPC Peering

### What is VPC Peering?
VPC Peering = দুটি VPC-র মধ্যে **direct network connection**। Private IP ব্যবহার করে communicate করে — internet-এর মাধ্যমে যায় না।

```
┌──────────────────────┐         ┌──────────────────────┐
│    VPC-A             │         │    VPC-B             │
│    10.0.0.0/16       │         │    10.1.0.0/16       │
│                      │         │                      │
│  ┌────────────┐      │         │  ┌────────────┐      │
│  │  App A     │◄─────┼─────────┼──┤  App B     │      │
│  │  10.0.1.5  │      │ Peering │  │  10.1.1.5  │      │
│  └────────────┘      │         │  └────────────┘      │
│                      │         │                      │
└──────────────────────┘         └──────────────────────┘

Properties:
  ✓ Private IP communication (not over internet)
  ✓ Low latency, high bandwidth
  ✓ Same region or cross-region
  ✗ CIDR blocks MUST NOT overlap
  ✗ NOT transitive: A↔B + B↔C ≠ A↔C
  ✗ Max ~125 peering connections per VPC
```

### Peering Limitations

```
Problem: 5 VPCs need full mesh communication

Mesh peering: 5 VPCs × (5-1)/2 = 10 peering connections
           ROUTES: Each VPC needs route to 4 others = 20 routes

Scale: 20 VPCs → 190 peerings → UNMANAGEABLE!

Solution: Transit Gateway (Hub-Spoke model)
```

## 4. Transit Gateway & Hub-Spoke

```
┌──────────────────────────────────────────────────────────────┐
│                    TRANSIT GATEWAY                           │
│                                                              │
│                    ┌──────────────┐                          │
│                    │   Transit    │                          │
│         ┌──────────┤   Gateway    ├──────────┐               │
│         │          │   (HUB)      │          │               │
│         │          └──────────────┘          │               │
│         │                                    │               │
│    ┌────▼────┐                          ┌────▼────┐          │
│    │  VPC-A  │                          │  VPC-C  │          │
│    │ Spoke 1 │                          │ Spoke 3 │          │
│    └─────────┘                          └─────────┘          │
│         │                                    │               │
│    ┌────▼────┐                          ┌────▼────┐          │
│    │  VPC-B  │                          │  VPC-D  │          │
│    │ Spoke 2 │                          │ Spoke 4 │          │
│    └─────────┘                          └─────────┘          │
│                                                              │
│  All VPCs connect to ONE Transit Gateway                     │
│  Any VPC can talk to any other VPC (if route table allows)  │
│  Connections: N VPCs = N attachments                         │
│  (vs N(N-1)/2 peerings for mesh)                             │
└──────────────────────────────────────────────────────────────┘
```

## 5. Kubernetes Multi-Cluster Networking

### Multi-Cluster Patterns

```
1. Single VPC, Multiple Clusters:
   VPC (10.0.0.0/16)
   ├── EKS Cluster A (10.0.32.0/19 for pods)
   ├── EKS Cluster B (10.0.64.0/19 for pods)
   └── Direct pod-to-pod across clusters (if CIDRs don't overlap)

2. Multiple VPCs, Transit Gateway:
   VPC-A (EKS-A) ── TGW ── VPC-B (EKS-B)
   → Pods in A can reach pods in B via TGW routes

3. Service Mesh Federation (Istio Multi-Cluster):
   - Istio control planes share service registry
   - mTLS between clusters
   - Services discoverable across clusters

4. Cilium ClusterMesh:
   - Pod IPs routable across clusters
   - Network policies span clusters
   - Global service load balancing
```

### Research Context

```
Multi-cluster monitoring:
  - Cross-cluster traffic patterns
  - VPN/peering link anomalies
  - Policy enforcement across clusters
  - East-west traffic analysis at scale
```

# Week 19 Quick Summary

```
Private Network = RFC 1918 IPs, isolated, internal use
Public Network  = Internet-routable IPs, exposed
VPN             = Encrypted tunnel over internet (Site-to-Site / Client)
Direct Connect  = Dedicated physical fiber (no internet)
VPC Peering     = Direct VPC-to-VPC connection (non-transitive)
Transit Gateway = Hub-spoke model → scalable inter-VPC routing
```
