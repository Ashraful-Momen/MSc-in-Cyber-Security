## 1. CoreDNS

### Architecture
```
┌──────────────────────────────────────────────────────────┐
│                     CoreDNS                              │
│                                                          │
│  Pod DNS Query: my-svc.default.svc.cluster.local         │
│         │                                                │
│         ▼                                                │
│  /etc/resolv.conf (in pod):                              │
│  nameserver 10.96.0.10  ← ClusterIP of kube-dns service  │
│  search default.svc.cluster.local svc.cluster.local      │
│  options ndots:5                                         │
│         │                                                │
│         ▼                                                │
│  CoreDNS Pod(s) — Deployment with Service                │
│  ┌────────────────────────────────────────┐              │
│  │ Plugins:                                │              │
│  │  • kubernetes — K8s service discovery  │              │
│  │  • forward   — external DNS forward    │              │
│  │  • cache     — DNS caching             │              │
│  │  • errors    — error logging           │              │
│  │  • log       — query logging           │              │
│  │  • prometheus — metrics                │              │
│  └────────────────────────────────────────┘              │
└──────────────────────────────────────────────────────────┘
```

### CoreDNS Configuration
```
Corefile:
  .:53 {
      errors
      health
      kubernetes cluster.local in-addr.arpa ip6.arpa {
         pods insecure
         fallthrough in-addr.arpa ip6.arpa
      }
      prometheus :9153
      forward . /etc/resolv.conf
      cache 30
      loop
      reload
      loadbalance
  }

Key Plugin: kubernetes
  - Watches K8s API for Services + Pods
  - Builds DNS records automatically
  - Service: my-svc.my-ns.svc.cluster.local → ClusterIP
  - Headless: pod-0.my-svc.my-ns.svc.cluster.local → Pod IP
```

### Research: DNS Monitoring
```
CoreDNS metrics (prometheus plugin):
  coredns_dns_requests_total{zone,proto,family,type}
  coredns_dns_responses_total{rcode}
  coredns_dns_request_duration_seconds

Anomaly detection:
  - NXDOMAIN spike → DGA malware in cluster?
  - DNS query latency spike → CoreDNS overload/attack
  - Unusual query types (TXT, MX) → DNS tunneling?
```

## 2. kube-proxy Deep Dive

```
kube-proxy = Per-node daemon that implements Service abstraction
             Watches API server → Programs iptables/IPVS/eBPF

┌──────────────────────────────────────────────────────────────┐
│                  kube-proxy Operation                        │
│                                                              │
│  1. Watch API Server for Services + Endpoints changes       │
│  2. On change: rebuild rules (iptables) or update (IPVS)    │
│  3. Program data plane to forward traffic                    │
│                                                              │
│  iptables mode issues at scale:                             │
│    - O(n) rules for n services (10K services = 50K+ rules)  │
│    - Rule updates = full table rewrite (disruption)          │
│    - No consistent load balancing algorithm                  │
│    - Debugging: iptables -t nat -L is nightmare at scale    │
│                                                              │
│  IPVS mode benefits:                                        │
│    - O(1) lookup in kernel (hash table)                     │
│    - Multiple schedulers: rr, lc, sh, dh, sed, nq           │
│    - Connection tracking more efficient                     │
│    - Use: >1000 services                                    │
└──────────────────────────────────────────────────────────────┘
```

## 3. CNI Specification

### What is CNI?
```
CNI (Container Network Interface) = Standard interface between
container runtime (CRI) and network plugins

CNI Flow:
  1. Container Runtime: "I need network for this pod"
  2. CNI: Calls configured plugin with CNI_ARGS
  3. Plugin: Creates veth, assigns IP, sets up routes
  4. Plugin: Returns result (IP, routes, DNS)
  5. Container Runtime: Configures pod network namespace

CNI Configuration:
  /etc/cni/net.d/*.conf  →  Which plugin to use
  /opt/cni/bin/          →  Plugin binaries
```

### CNI Operations
```
ADD:    Create network for new pod
DEL:    Remove network when pod deleted
CHECK:  Verify pod networking is working
VERSION: Plugin version info

CNI JSON Result:
{
  "cniVersion": "0.3.1",
  "interfaces": [{ "name": "eth0" }],
  "ips": [{ "address": "10.244.1.2/24", "gateway": "10.244.1.1" }],
  "routes": [{ "dst": "0.0.0.0/0", "gw": "10.244.1.1" }],
  "dns": { "nameservers": ["10.96.0.10"], "search": ["default.svc.cluster.local"] }
}
```

## 4. Flannel

### Overview
```
Flannel = Simplest CNI — focuses ONLY on pod network connectivity
          L2/L3 connectivity across nodes via overlay (VXLAN or host-gw)

Modes:
  VXLAN:   Encapsulate pod traffic in VXLAN (UDP 8472)
           Default, works everywhere
  host-gw: Direct routing (no encapsulation)
           Faster, but needs L2 adjacency between nodes
  UDP:     Userspace encapsulation (slow, deprecated)

Flannel is SIMPLE but MINIMAL:
  ✓ Pod-to-pod connectivity
  ✗ No NetworkPolicy support (use Calico policy-only mode with Flannel)
  ✗ No encryption
  ✗ No advanced features
```

## 5. Calico

### Overview
```
Calico = Full-featured CNI with BGP-based routing + NetworkPolicy
         NO overlay (by default) — pure L3 routing

Architecture:
  ┌────────────────────────────────────────────────────────┐
  │                     Calico                             │
  │                                                        │
  │  calico-node (DaemonSet on each node):                 │
  │  ┌──────────────────────────────────────────┐         │
  │  │ • Felix     — Programs iptables/eBPF     │         │
  │  │              (NetworkPolicy enforcement) │         │
  │  │ • BIRD      — BGP daemon                 │         │
  │  │              (Route propagation)         │         │
  │  │ • confd     — Configuration from etcd    │         │
  │  └──────────────────────────────────────────┘         │
  │                                                        │
  │  calico-kube-controllers:                              │
  │  ┌──────────────────────────────────────────┐         │
  │  │ • Policy Controller                     │         │
  │  │ • Namespace Controller                  │         │
  │  │ • ServiceAccount Controller             │         │
  │  │ • Node Controller                       │         │
  │  └──────────────────────────────────────────┘         │
  └────────────────────────────────────────────────────────┘
```

### Calico Modes

```
1. BGP (Native — default):
   - Nodes peer via BGP → exchange pod CIDR routes
   - No overlay, no encapsulation (best performance)
   - Requires BGP-capable network (or BGP route reflector)
   - IP-in-IP tunnel for subnets that can't route directly

2. VXLAN Cross-Subnet:
   - BGP within subnet, VXLAN across subnets
   - Best of both: performance where possible, overlay where needed

3. eBPF Mode (NEW — direct replacement for kube-proxy + iptables):
   - Services implemented via eBPF (no kube-proxy needed!)
   - Direct Server Return (DSR) for external traffic
   - Better performance + observability
```

## 6. Cilium (eBPF-based) — ⭐ MOST IMPORTANT FOR RESEARCH

### Overview
```
Cilium = Next-gen CNI built on eBPF
         Networking + Security + Observability — ALL in eBPF

Why Cilium Matters for Your Research:
  ✓ eBPF-based → direct kernel-level visibility
  ✓ Hubble → network flow observability built-in
  ✓ L7 Network Policies (HTTP, gRPC, Kafka)
  ✓ Identity-based security (not just IP-based)
  ✓ Transparent encryption (WireGuard/IPSec)
  ✓ Service mesh replacement (no sidecar needed!)
```

### Cilium Architecture
```
┌──────────────────────────────────────────────────────────────┐
│                       CILIUM                                 │
│                                                              │
│  Per-Node Agent (DaemonSet):                                 │
│  ┌────────────────────────────────────────────────────┐     │
│  │                                                    │     │
│  │  Cilium Agent ──► eBPF Programs loaded in kernel   │     │
│  │                    ┌─────────────────────┐         │     │
│  │                    │ eBPF Programs:      │         │     │
│  │                    │ • Connectivity      │         │     │
│  │                    │ • Load Balancing    │         │     │
│  │                    │ • Network Policy    │         │     │
│  │                    │ • Observability     │         │     │
│  │                    │ • Encryption        │         │     │
│  │                    └─────────────────────┘         │     │
│  │                                                    │     │
│  │  Hubble ──► Flow observability (L3/L4/L7)         │     │
│  │            Service dependency graph               │     │
│  │            Network metrics + monitoring            │     │
│  └────────────────────────────────────────────────────┘     │
│                                                              │
│  Cilium Operator: IPAM, cluster management                  │
└──────────────────────────────────────────────────────────────┘
```

### Cilium eBPF Data Path

```
Traditional (iptables):
  Packet → iptables (50K rules, O(n)) → route → pod
  SLOW + complex at scale

Cilium eBPF:
  Packet → eBPF program (hash table, O(1)) → route → pod
  FAST + efficient + observable

eBPF hooks:
  - TC (Traffic Control): Ingress/egress on veth interfaces
  - XDP (eXpress Data Path): Earliest attach point on NIC
  - Socket: Per-socket operations
  - cgroup: Per-cgroup (pod) operations
```

### Hubble — Built-in Observability (YOUR RESEARCH TOOL!)

```bash
# Enable Hubble in Cilium
cilium hubble enable

# Observe all flows in cluster
cilium hubble observe

# Filtered observation
cilium hubble observe --namespace production
cilium hubble observe --from-pod app-xxx --to-pod db-yyy
cilium hubble observe --verdict DROPPED    # See blocked traffic!

# Hubble UI — Service Map
cilium hubble ui
# Opens dashboard showing:
#  - Service dependency graph (auto-discovered!)
#  - Flow latency between services
#  - HTTP/gRPC method + paths
#  - DROPPED traffic (NetworkPolicy violations)

# Hubble exports flow logs → JSON → Your ML dataset!
```

### Research Integration with Cilium

```
Cilium + Hubble → Automated Dataset Pipeline:

1. Hubble Flow Logs:
   {
     "time": "2024-01-15T10:30:00Z",
     "source": {"identity": "12345", "pod": "frontend-xxx", "namespace": "prod"},
     "destination": {"identity": "67890", "pod": "api-yyy", "namespace": "prod"},
     "verdict": "FORWARDED" | "DROPPED",
     "l4": {"TCP": {"source_port": 45678, "destination_port": 8080}},
     "l7": {"type": "HTTP", "http": {"method": "GET", "url": "/users"}},
     "event_type": {"type": "L7"},
     "summary": "HTTP/1.1 GET http://api-svc.prod.svc.cluster.local/users"
   }

2. Extract → Label:
   FORWARDED flows = Normal (0)
   DROPPED flows = Potential Attack / Policy Violation (1)

3. Features per flow:
   source_identity, dest_identity, source_pod, dest_pod
   source_namespace, dest_namespace, l4_protocol, port
   l7_method, l7_path, l7_status
   flow_duration, bytes_sent, bytes_received
   verdict (FORWARDED/DROPPED/ERROR)

4. ML Model:
   Input: Flow features from Hubble
   Output: Anomaly score (with SHAP explanation)

This is production-grade, research-ready pipeline!
```
