## 1. NetworkPolicy Fundamentals

```
NetworkPolicy = Kubernetes-native firewall rules for pod traffic
                "Which pods can talk to which pods, on which ports?"

DEFAULT BEHAVIOR (without NetworkPolicy):
  ALL pods can communicate with ALL other pods
  ALL namespaces → cross-namespace traffic ALLOWED
  (This is INSECURE by default!)

WITH NetworkPolicy:
  Only explicitly ALLOWED traffic passes
  Everything else → DENIED
  (Least privilege model)
```

### Basic NetworkPolicy

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: api-allow-from-frontend
  namespace: production
spec:
  podSelector:
    matchLabels:
      app: api-server          # Applies TO these pods
  policyTypes:
  - Ingress                    # Controls INCOMING traffic
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: frontend         # ALLOW from pods with this label
    - namespaceSelector:
        matchLabels:
          team: platform        # ALLOW from specific namespace
    - ipBlock:
        cidr: 10.0.0.0/8       # ALLOW from IP range
        except:
        - 10.0.0.0/16          #  EXCEPT this block
    ports:
    - protocol: TCP
      port: 8080               # ONLY on port 8080
```

## 2. Policy Types + Selectors

### Ingress vs Egress

```yaml
# Ingress only: Control who can talk TO this pod
spec:
  policyTypes: [Ingress]
  podSelector: {app: database}
  ingress:
  - from:
    - podSelector: {app: api}

# Egress only: Control where this pod can talk TO
spec:
  policyTypes: [Egress]
  podSelector: {app: batch-job}
  egress:
  - to:
    - podSelector: {app: api}
    ports:
    - protocol: TCP
      port: 443

# Both! Most secure
spec:
  policyTypes: [Ingress, Egress]
```

### Selector Combinations

```yaml
# AND logic within a 'from' entry
ingress:
- from:
  - podSelector: {app: frontend}
    namespaceSelector: {team: web}    # Both must match (AND)

# OR logic with multiple 'from' entries
ingress:
- from:
  - podSelector: {app: frontend}      # Match this (OR)
  - namespaceSelector: {name: monitoring}  # OR this
```

### Default Deny Policies

```yaml
# Default deny ALL ingress (whitelist approach)
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: production
spec:
  podSelector: {}                # {} = ALL pods in namespace
  policyTypes: [Ingress]
  # No ingress rules = DENY ALL

# Result: No pod in 'production' can receive ANY traffic
#         unless another policy explicitly ALLOWS it
```

## 3. Pod Communication Patterns

```
┌──────────────────────────────────────────────────────────────┐
│              POD COMMUNICATION PATTERNS                       │
│                                                              │
│  1. Intra-Pod (Containers within same Pod):                  │
│     Container A ◄── localhost ──► Container B               │
│     Same network namespace, always allowed                   │
│                                                              │
│  2. Intra-Node (Pods on same node):                          │
│     Pod A ◄── cni0 bridge ──► Pod B                         │
│     Via node's pod network bridge                            │
│                                                              │
│  3. Inter-Node (Pods on different nodes):                    │
│     Pod A ◄── CNI routing ──► Pod C                         │
│     Overlay (VXLAN) or direct routing (BGP)                  │
│                                                              │
│  4. Pod → Service (via ClusterIP):                           │
│     Pod ◄── kube-proxy DNAT ──► Service VIP ──► Backend Pod │
│                                                              │
│  5. Pod → External (internet):                               │
│     Pod → Node MASQUERADE (SNAT) → Internet                 │
│     Pod IP hidden behind node IP                             │
│                                                              │
│  6. External → Pod (via LB/NodePort/Ingress):                │
│     Internet → LB → NodePort → kube-proxy → Pod             │
└──────────────────────────────────────────────────────────────┘
```

### Policy Coverage Matrix

```
Design: Which policies do you need?

┌────────────────────┬──────────────────────────────────────────┐
│ Traffic Direction  │ Policy                                    │
├────────────────────┼──────────────────────────────────────────┤
│ Frontend → API     │ NP: allow from frontend to api (8080)    │
│ API → Database     │ NP: allow from api to db (5432)          │
│ Monitoring → All   │ NP: allow from monitoring to all (metrics)│
│ Internet → Ingress │ N/A (handled by Ingress Controller)      │
│ API → Payment API  │ NP: allow from api to payment (mTLS 8443)│
│ All → kube-DNS     │ NP: allow to kube-system/coredns (53)    │
│ * → * (default)    │ NP: default-deny all (DELETE this!)      │
└────────────────────┴──────────────────────────────────────────┘
```

## 4. Namespace Isolation

### Namespace-Level Default Deny

```yaml
# Apply to EVERY namespace for zero-trust posture:
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: production
spec:
  podSelector: {}
  policyTypes:
  - Ingress
  - Egress
---
# Then explicit allows:
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-dns
  namespace: production
spec:
  podSelector: {}
  policyTypes: [Egress]
  egress:
  - to:
    - namespaceSelector:
        matchLabels:
          name: kube-system
    - podSelector:
        matchLabels:
          k8s-app: kube-dns
    ports:
    - protocol: UDP
      port: 53
```

### Label-Based Access Control

```yaml
# Allow only from same namespace with specific label
ingress:
- from:
  - podSelector:
      matchLabels:
        access-tier: trusted
    namespaceSelector:
      matchLabels:
        environment: production

# Block cross-namespace entirely
# Simply don't include namespaceSelector in your allows
# Default-deny handles the rest
```

## 5. Policy Enforcement (CNI Implementation)

### Calico Implementation
```
Calico translates NetworkPolicy → iptables rules (or eBPF)

iptables mode:
  iptables -L cali-pi-xxx → per-policy chains
  iptables -L cali-po-xxx → per-pod profile chains
  (Similar to kube-proxy but for policy enforcement)

eBPF mode (Cilium-style):
  eBPF program attached to pod veth interface
  → Checks policy at kernel level → FORWARD/DROP
  → O(1) lookup, no iptables complexity
```

### Cilium Implementation
```
Cilium maps NetworkPolicy → eBPF programs:

1. Identity-based (not IP-based!):
   Each pod gets cryptographic identity
   Policy: "allow identity=frontend → identity=api on port 8080"
   (If pod restarts with new IP → policy still works automatically!)

2. L7 enforcement in eBPF:
   HTTP GET /users → ALLOW
   HTTP POST /admin → DENY
   gRPC CreateOrder → ALLOW
   (Specific API calls enforced at kernel level!)

3. Policy verdict in Hubble:
   DROPPED flow → reason: "Policy denied (egress default deny)"
   → Direct feature for anomaly detection!
```

## 6. Research: Policy-based Anomaly Detection

### Detection Logic

```
NetworkPolicy defines EXPECTED behavior:

  Expected: Frontend → API (port 8080) : ALLOWED
            API → Database (port 5432)  : ALLOWED
            Monitoring → All (metrics)  : ALLOWED

  Anomaly:  Frontend → Database (port 5432) : DROPPED ← ATTEMPT!
            Random pod → kube-apiserver (6443) : DROPPED ← ATTEMPT!
            Database → Internet (443) : DROPPED ← DATA EXFIL!

Detection Rule:
  IF traffic.verdict == DROPPED AND source NOT in expected_sources:
      → ALERT: Potential attack / misconfiguration
      → Feature: "policy_violation" = True
      → SHAP: "Policy X denied this traffic"
```

### Dataset Integration

```python
# Policy violation as ML feature

# From Hubble/Cilium flow logs:
flows = [
    {"src": "frontend-xxx", "dst": "api-yyy", "port": 8080, "verdict": "FORWARDED"},
    {"src": "frontend-xxx", "dst": "db-zzz", "port": 5432, "verdict": "DROPPED"},
    {"src": "unknown-pod", "dst": "kube-apiserver", "port": 6443, "verdict": "DROPPED"},
]

# Features:
# - forward_count_per_src (normal behavior baseline)
# - dropped_count_per_src (anomaly indicator)
# - dropped_to_forward_ratio (key metric)
# - policy_hit_count (which policies are triggered)
# - destination_diversity (scanning detection)
# - is_cross_namespace (lateral movement indicator)
# - protocol_mismatch (e.g., TCP to expected-UDP service)
```

# Research: Kubernetes Threat Detection Framework

```
┌──────────────────────────────────────────────────────────────────┐
│            NETWORK POLICY → THREAT DETECTION                     │
│                                                                  │
│  Step 1: Baseline (Normal)                                       │
│    Collect NetworkPolicy + Flow logs for 1 week                  │
│    Establish per-service communication graph                     │
│    Expected: {src: [allowed_destinations]}                      │
│                                                                  │
│  Step 2: Feature Engineering                                     │
│    Per source pod:                                               │
│      - connection_rate_out, connection_rate_in                  │
│      - unique_destinations, unique_ports                        │
│      - policy_denied_rate (DROPPED / total)                    │
│      - cross_namespace_ratio                                    │
│      - l7_method_distribution (HTTP GET/POST ratio)            │
│                                                                  │
│  Step 3: Anomaly Detection → ML                                  │
│    Train: Autoencoder / Isolation Forest on normal data          │
│    Detect: Deviation from baseline patterns                      │
│                                                                  │
│  Step 4: Explain → SHAP                                          │
│    Why flagged?                                                  │
│    "High policy_denied_rate (0.45 vs baseline 0.01)"            │
│    "Unexpected destination: db-zzz (not in allowed list)"       │
│    "New port accessed: 5432 (not in service definition)"        │
│                                                                  │
│  Step 5: Alert → Security Response                               │
│    Severity: policy_denied_rate × destination_sensitivity       │
│    e.g., "Frontend→DB denied" = MEDIUM                          │
│          "Unknown→kube-apiserver denied" = HIGH                  │
└──────────────────────────────────────────────────────────────────┘
```
