## 1. Docker Networking Overview

### Docker Network Drivers

```
┌────────────────┬──────────────────────────────────────────────────┐
│ Driver         │ Description                                      │
├────────────────┼──────────────────────────────────────────────────┤
│ bridge (default)│ Docker host-এ private internal network           │
│                │ Containers communicate via bridge                │
│                │ NAT for external access                          │
├────────────────┼──────────────────────────────────────────────────┤
│ host           │ Container shares host's network stack            │
│                │ No isolation — same IP as host                   │
│                │ Best performance, no security                    │
├────────────────┼──────────────────────────────────────────────────┤
│ overlay        │ Multi-host container communication               │
│                │ For Docker Swarm / cross-host pods               │
│                │ VXLAN tunnel encapsulation                       │
├────────────────┼──────────────────────────────────────────────────┤
│ macvlan        │ Container gets its own MAC address                │
│                │ Appears as separate physical device on LAN        │
│                │ Direct access to physical network                │
├────────────────┼──────────────────────────────────────────────────┤
│ none           │ No networking — container has only loopback       │
│                │ Use when you manually configure networking        │
└────────────────┴──────────────────────────────────────────────────┘
```

### Docker Network Commands

```bash
# List networks
docker network ls

# Inspect network (see connected containers, IPAM, subnet)
docker network inspect bridge

# Create custom network
docker network create --driver bridge --subnet 172.20.0.0/16 my-net

# Connect container to network
docker run --network my-net --name app nginx
docker network connect my-net existing-container

# Disconnect
docker network disconnect my-net container-name
```

## 2. Bridge Network

### Default Bridge (docker0)

```
┌──────────────────────────────────────────────────────────────────┐
│                        DOCKER HOST                                │
│                                                                  │
│    Physical Network (192.168.1.0/24)                             │
│    └── eth0: 192.168.1.5                                        │
│                                                                  │
│    Docker Bridge Network (172.17.0.0/16)                        │
│    ┌────────────────────────────────────────────────┐            │
│    │            docker0 (bridge)                     │            │
│    │            172.17.0.1                           │            │
│    │                                                │            │
│    │   ┌───────────┐   ┌───────────┐   ┌──────────┐ │            │
│    │   │ Container │   │ Container │   │Container │ │            │
│    │   │    A      │   │    B      │   │    C     │ │            │
│    │   │172.17.0.2 │   │172.17.0.3 │   │172.17.0.4│ │            │
│    │   │veth-xxx◄──┼───┼──►veth-yyy│   │veth-zzz  │ │            │
│    │   └───────────┘   └───────────┘   └──────────┘ │            │
│    └────────────────────────────────────────────────┘            │
│                                                                  │
│    External access: Container → docker0 → NAT (iptables) → eth0 │
│    Internal access: Container A ↔ docker0 ↔ Container B          │
└──────────────────────────────────────────────────────────────────┘
```

### Bridge Network Internals

```bash
# Docker creates:
# 1. Bridge interface
ip link show docker0
# docker0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500

# 2. iptables rules for NAT
sudo iptables -t nat -L POSTROUTING -n -v
# MASQUERADE  all  --  172.17.0.0/16  0.0.0.0/0

# 3. veth pair per container
ip link show | grep veth
# veth12345@if6: <BROADCAST,MULTICAST,UP,LOWER_UP>

# 4. Each container has:
#    - eth0 interface (container side of veth)
#    - IP from bridge subnet
#    - Default route via docker0 IP
```

### Custom Bridge Network

```bash
# Create custom bridge (better than default for many reasons)
docker network create \
  --driver bridge \
  --subnet 10.100.0.0/24 \
  --gateway 10.100.0.1 \
  --ip-range 10.100.0.128/25 \
  my-app-net

# Benefits over default bridge:
# ✓ Automatic DNS resolution (container name → IP)
# ✓ User-defined subnet
# ✓ Isolation between custom networks
# ✓ Containers on same custom network can resolve each other by name

docker run --network my-app-net --name db -d postgres:15
docker run --network my-app-net --name app -d my-app:latest

# app can reach db as: postgres://db:5432/
# Docker's embedded DNS resolves "db" → 10.100.0.x
```

### Bridge Network Problems

```
1. Single Host Only:
   Containers on different Docker hosts CANNOT communicate
   → Need overlay network or external solutions

2. NAT Overhead:
   External access requires port mapping (-p 8080:80)
   iptables rules overhead at scale

3. IP Exhaustion:
   Default 172.17.0.0/16 = 65K IPs (enough for one host)
   But custom subnets may be limited

4. No Direct Reachability:
   Container IP is private — not routable from outside host
```

## 3. Host Network

### Host Network Mode

```
┌──────────────────────────────────────────────────┐
│              DOCKER HOST                          │
│                                                   │
│  eth0: 192.168.1.5                                │
│  lo: 127.0.0.1                                    │
│                                                   │
│  ┌─────────────────────────────────────────────┐ │
│  │ Container (--network host)                  │ │
│  │ SHARES host's network namespace             │ │
│  │                                             │ │
│  │ ifconfig shows: eth0=192.168.1.5 (same!)    │ │
│  │                 lo=127.0.0.1                │ │
│  └─────────────────────────────────────────────┘ │
│                                                   │
│  Container port 80 = Host port 80                │
│  (No port mapping needed, no NAT)                │
│  Performance: BEST (no network namespace overhead)│
│  Security: WORST (full host network access)      │
└──────────────────────────────────────────────────┘
```

### When to Use Host Network

```
✓ High-performance networking (packet processing, DPDK)
✓ Monitoring agents (need host network visibility)
✓ Kubernetes: hostNetwork: true for DaemonSets
  (e.g., Calico node, kube-proxy, node-exporter)

✗ Multi-container on same host (port conflicts!)
✗ Security-sensitive workloads (no isolation)
```

## 4. Overlay Network

### What is Overlay Network?

```
Overlay network = L2 network OVER L3 infrastructure
                 VXLAN tunnel-এর মাধ্যমে encapsulation

┌─────────────────────┐          ┌─────────────────────┐
│     Host A          │          │     Host B          │
│                     │          │                     │
│ Container X         │          │ Container Y         │
│ 10.0.9.3            │          │ 10.0.9.4            │
│    │                │          │    │                │
│    ▼                │          │    ▼                │
│ docker_gwbridge     │          │ docker_gwbridge     │
│    │                │          │    │                │
│    ▼                │          │    ▼                │
│ VXLAN Tunnel Endpoint│◄══════►│ VXLAN Tunnel Endpoint│
│    │                │  VXLAN   │    │                │
│    ▼                │  tunnel  │    ▼                │
│ eth0: 192.168.1.5   │          │ eth0: 192.168.1.6   │
└─────────────────────┘          └─────────────────────┘

Container X (10.0.9.3) → ping → Container Y (10.0.9.4):
  1. X sends packet: dst=10.0.9.4
  2. VXLAN encapsulates: outer IP dst=192.168.1.6, UDP port 4789
  3. Physical network routes outer packet → Host B
  4. Host B decapsulates → delivers to Container Y

X and Y think they're on same L2 network!
```

### Docker Overlay Network

```bash
# Initialize Swarm (overlay needs Swarm mode or external KV store)
docker swarm init

# Create overlay network
docker network create \
  --driver overlay \
  --subnet 10.0.9.0/24 \
  --attachable \
  my-overlay-net

# Run services across nodes
docker service create --name web --network my-overlay-net --replicas 3 nginx

# Containers on different hosts can communicate via overlay
```

### Overlay in Kubernetes

```
Kubernetes CNI overlay same concept:
  Flannel VXLAN mode → overlay
  Calico with VXLAN → overlay
  Weave → overlay

Cross-node pod communication:
  Pod A (Node 1) → VXLAN tunnel → Pod B (Node 2)
  Underlay: node IPs   Overlay: pod IPs
```

## 5. Macvlan Network

### What is Macvlan?

```
Macvlan = Container gets its own MAC address
          Appears as SEPARATE physical device on the LAN

┌──────────────────────────────────────────────────────┐
│              Physical Network (192.168.1.0/24)        │
│                                                      │
│  ┌─────────┐  ┌──────────┐  ┌──────────┐            │
│  │ Host    │  │Container │  │Container │            │
│  │eth0     │  │macvlan0  │  │macvlan1  │            │
│  │.1.5     │  │.1.50     │  │.1.51     │            │
│  │MAC:aa:bb│  │MAC:cc:dd │  │MAC:ee:ff │            │
│  └─────────┘  └────┬─────┘  └────┬─────┘            │
│                    │             │                   │
│                    └──────┬──────┘                   │
│                           │                          │
│              ┌────────────▼──────────┐               │
│              │  Physical Switch      │               │
│              └───────────────────────┘               │
└──────────────────────────────────────────────────────┘

Router/switch sees 3 SEPARATE devices:
  MAC aa:bb → 192.168.1.5  (Host)
  MAC cc:dd → 192.168.1.50 (Container 1)
  MAC ee:ff → 192.168.1.51 (Container 2)

Each container has direct LAN access — no NAT!
```

### Macvlan Modes

```
Bridge Mode:
  Containers on same host can communicate via macvlan bridge
  Containers get unique MACs on the physical network
  Most commonly used

Private Mode:
  Containers on same host CANNOT communicate
  Each container isolated even from siblings
  Use: multi-tenant security

Passthru Mode:
  Single container gets direct exclusive access to physical NIC
  Parent interface can't be used by host
  Use: VM-like direct hardware access (DPDK, SR-IOV)
```

```bash
# Create macvlan network
docker network create \
  --driver macvlan \
  --subnet 192.168.1.0/24 \
  --gateway 192.168.1.1 \
  --ip-range 192.168.1.192/27 \
  -o parent=eth0 \
  my-macvlan-net

# Run container with static IP on LAN
docker run --network my-macvlan-net --ip 192.168.1.200 -d nginx
```

### Macvlan Limitations

```
1. Host cannot communicate with its own macvlan containers
   (Linux kernel limitation — hairpin routing needed)

2. MAC address table pressure on physical switch
   (100s of containers = 100s of MAC addresses)

3. No port mapping (container IP = direct LAN IP)

4. Most cloud providers don't support promiscuous mode
   → Macvlan doesn't work in AWS/GCP/Azure
```

## 6. Container → Kubernetes Mapping

```
┌────────────────────┬────────────────────────────────────────┐
│ Docker Concept     │ Kubernetes Equivalent                  │
├────────────────────┼────────────────────────────────────────┤
│ Container          │ Container (inside Pod)                 │
│ Bridge Network     │ Pod network (CNI bridge: cni0/cbr0)   │
│ Port Mapping (-p)  │ Service (ClusterIP/NodePort/LB)       │
│ --link (legacy)    │ Service discovery (DNS + labels)      │
│ docker-compose     │ Kubernetes manifests + Services        │
│ Overlay Network    │ CNI overlay (Flannel VXLAN, Calico)   │
│ Host Network       │ hostNetwork: true (Pod spec)           │
│ Network Policy     │ Kubernetes NetworkPolicy               │
│ Custom Bridge      │ CNI-specific network config            │
│ DNS Resolution     │ CoreDNS (svc.cluster.local)            │
└────────────────────┴────────────────────────────────────────┘

Key Difference:
  Docker: One container = one IP (on bridge network)
  Kubernetes: One POD = one IP (all containers in pod share IP)
              Containers within pod communicate via localhost!
```

### Docker Bridge → Kubernetes Pod Network

```
Docker Bridge:
  docker0 ─── veth ─── Container (own network namespace)
  (Docker manages bridge + veth + IPAM)

Kubernetes CNI:
  cni0 ─── veth ─── Pod (own network namespace)
  ─── veth ─── Pod
  (CNI plugin manages bridge + veth + IPAM)
  But ADDITIONALLY:
  - Cross-node routing (overlay or BGP)
  - NetworkPolicy enforcement (iptables/eBPF)
  - Service abstraction (ClusterIP, kube-proxy)
```

# Research Context

```
Container Networking → Kubernetes Security Dataset:

1. Container network interface stats:
   /sys/class/net/<veth>/statistics/
   → RX/TX bytes, packets, errors, drops
   → Per-pod network metrics

2. Docker bridge MAC learning:
   bridge fdb show br docker0
   → MAC-to-port mapping → pod connectivity graph

3. Overlay tunnel metrics:
   VXLAN packet count, fragmentation
   → Cross-node pod communication health

4. Network namespace inspection:
   lsns -t net → all network namespaces
   → Pod/container inventory for monitoring
```
