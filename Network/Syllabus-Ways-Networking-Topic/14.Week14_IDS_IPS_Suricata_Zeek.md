## 1. IDS vs IPS

### IDS (Intrusion Detection System)
```
                    ┌──────────┐
    Traffic ──────► │   IDS    │ ──► ALERT (notification only)
    (copy)          │ (monitor)│     ✗ Does NOT block traffic
                    └──────────┘

    IDS = Security camera — দেখে + রিপোর্ট করে, কিন্তু থামায় না
    Deployment: SPAN port / TAP (passive, out-of-band)
```

### IPS (Intrusion Prevention System)
```
                    ┌──────────┐
    Traffic ──────► │   IPS    │ ──► BLOCK (if malicious)
    (inline)         │ (active) │     ✓ Can drop malicious packets
                    └──────────┘

    IPS = Security guard — দেখে + থামায়
    Deployment: Inline (traffic flows THROUGH IPS)
```

### Comparison

```
┌───────────────┬──────────────────────┬─────────────────────────┐
│ Feature       │ IDS                  │ IPS                      │
├───────────────┼──────────────────────┼─────────────────────────┤
│ Position      │ Out-of-band (copy)   │ Inline (through)         │
│ Failure Mode  │ Fails silent (no     │ Fails open (pass traffic)│
│               │ impact on traffic)   │ or fail close (block all)│
│ Latency       │ None                 │ Adds processing delay    │
│ Action         │ Alert only           │ Alert + Block            │
│ False Positive │ Annoying alert        │ Block legitimate traffic!│
│ Deployment    │ Easy (SPAN port)      │ Complex (network change) │
│ Use Case      │ Monitoring, forensics │ Real-time prevention     │
└───────────────┴──────────────────────┴─────────────────────────┘
```

### Deployment Architecture

```
┌──────────────────────────────────────────────────────────────────┐
│                     IDS + IPS DEPLOYMENT                         │
│                                                                  │
│   Internet ──► Router ──► Firewall ──► IPS (inline) ──► Switch  │
│                                       │                          │
│                                       ▼                          │
│                                    BLOCK malicious              │
│                                                                  │
│                         Switch ──► SPAN Port ──► IDS (passive)  │
│                                                  │               │
│                                                  ▼               │
│                                              ALERT only         │
│                                                                  │
│   IDS + IPS together:                                           │
│   IPS = real-time blocking                                      │
│   IDS = deep analysis + forensics + rule tuning                 │
└──────────────────────────────────────────────────────────────────┘
```

## 2. Detection Methodologies

### Signature-Based Detection
```
Pattern matching against known attack signatures:

  Rule: alert tcp any any -> any 80 (msg:"SQL Injection";
        content:"' OR '1'='1"; nocase; sid:1000001;)

  ✓ Fast, low false positive for known attacks
  ✗ Cannot detect new/unknown attacks (0-day blind)
  ✗ Signature database must be updated
  ✗ Evasion: slight modification bypasses signature
```

### Anomaly-Based Detection
```
Baseline "normal" behavior → detect deviations:

  Baseline: avg HTTP requests = 100/min, avg DNS queries = 50/min
  Anomaly: HTTP = 5000/min, DNS = 2000/min → ALERT!

  ✓ Can detect unknown/0-day attacks
  ✓ Adaptable to environment
  ✗ Higher false positive rate
  ✗ Needs training period for baseline
  ✗ "Normal" can change over time (baseline drift)
```

### Behavior-Based / Heuristic
```
Detect suspicious behavior patterns:

  - Port scan: Many SYN to many ports from single IP
  - Brute force: Many login failures
  - Data exfiltration: Large outbound transfer at 3 AM
  - Lateral movement: Internal IP scanning other internal IPs

  More sophisticated than signature, more targeted than anomaly
```

### Comparison

```
┌─────────────────┬──────────────────┬──────────────────┬──────────────┐
│ Method          │ Strength         │ Weakness         │ Example      │
├─────────────────┼──────────────────┼──────────────────┼──────────────┤
│ Signature       │ Precise, fast    │ 0-day blind      │ Snort rules  │
│ Anomaly         │ Unknown threats  │ False positives  │ ML models    │
│ Behavior/Heuristic│ Attack patterns │ Complex tuning   │ Zeek scripts │
│ Protocol Analysis│ RFC violations   │ Legitimate bugs  │ Suricata     │
│ Reputation      │ Known bad IPs    │ IP churn         │ Threat Intel │
└─────────────────┴──────────────────┴──────────────────┴──────────────┘
```

## 3. Suricata

### Overview
Suricata — high-performance, multi-threaded IDS/IPS engine। Snort-compatible rules + modern features (JSON output, Lua scripting, file extraction)।

```bash
# Install
sudo apt install suricata

# Check version
suricata --build-info
```

### Suricata Modes

```bash
# IDS mode (passive — alert only)
sudo suricata -i eth0 -c /etc/suricata/suricata.yaml

# IPS mode (inline — block traffic, requires NFQUEUE)
sudo suricata -q 0 -c /etc/suricata/suricata.yaml

# PCAP analysis mode (offline — analyze existing capture)
suricata -r capture.pcap -c /etc/suricata/suricata.yaml -l logs/

# Test mode (check config + rules)
suricata -T -c /etc/suricata/suricata.yaml
```

### Key Output Files

```bash
ls -la /var/log/suricata/

# eve.json    → Structured JSON events (ALL events — research gold!)
# fast.log     → Simple alert summary (grep-friendly)
# stats.log    → Performance statistics
# http.log     → HTTP request logs
# dns.log      → DNS query logs
# tls.log      → TLS handshake logs
# drop.log     → Dropped packets (IPS mode)
```

```
Suricata captures per-flow:
  - Protocol metadata (HTTP headers, DNS queries, TLS SNI/JA3)
```

## 4. Zeek (formerly Bro)

### Overview
Zeek — network security monitor, NOT signature-based IDS। Event-driven scripting engine — traffic দেখে events generate করে, scripts analyze করে।

```
Zeek Philosophy (vs Suricata/Snort):

Suricata: "Does packet match known attack signature? → ALERT"
Zeek:     "What happened on the network? → LOG EVERYTHING"

Zeek is a network metadata extraction engine first,
intrusion detection second.
```

### Key Zeek Logs

```bash
# Default log directory
ls /usr/local/zeek/logs/current/

# conn.log          → Every TCP/UDP/ICMP connection (FLOW SUMMARY!)
# dns.log           → Every DNS query/response
# http.log          → Every HTTP request/response
# ssl.log           → Every TLS/SSL session (SNI, cert, JA3!)
# ftp.log           → FTP sessions
# smtp.log          → Email transactions
# ssh.log           → SSH sessions
# files.log         → Files transferred over network
# x509.log          → SSL/TLS certificates seen
# notice.log         → Zeek notices (potential issues)
# weird.log          → Protocol anomalies/violations
# known_hosts.log   → Hosts seen on network
# known_services.log → Services detected
```

### conn.log — The Master Flow Log

```
#fields	ts	uid	id.orig_h	id.orig_p	id.resp_h	id.resp_p	proto	service	duration	orig_bytes	resp_bytes	conn_state ...

# Example connection:
  1234567890.123  CAbCdE123  192.168.1.5  52341  93.184.216.34  443  tcp  ssl  15.234  1500  48000  SF

# Key Fields:
  uid           : Unique connection ID (join key for all logs!)
  id.orig_h/p   : Source IP + Port
  id.resp_h/p   : Destination IP + Port
  proto         : tcp, udp, icmp
  service       : Detected L7 protocol (http, dns, ssl, ssh)
  duration      : Connection duration (seconds)
  orig_bytes    : Client → Server bytes
  resp_bytes    : Server → Client bytes
  conn_state    : Connection state summary
                  S0=SYN only, S1=Established, SF=Normal close
                  RST=Reset, S2=SYN+ACK seen, S3=SYN only (scan!)

This ONE log is the perfect foundation for ML flow dataset!
```

### Research Context — Zeek is PERFECT for ML

```
Zeek conn.log → Direct ML Dataset:

1. Flow-level by default (no packet aggregation needed!)
2. Rich metadata per connection
3. Structured logs (tab-separated, easy to parse)
4. Protocol-specific logs (dns, http, ssl) join on uid
5. Connection state already summarized (conn_state)

ML Feature Engineering from Zeek logs:

Join conn.log + dns.log + http.log + ssl.log on uid
→ Per-connection feature vector:
  [duration, orig_bytes, resp_bytes, proto, service, conn_state,
   dns_query, dns_rcode, http_method, http_status,
   ssl_sni, ssl_ja3, ...]

This is what production ML pipelines use!
```

## 5. Basic Rules

### Suricata/Snort Rule Structure

```
alert tcp $HOME_NET any -> $EXTERNAL_NET 80 (
  msg:"Possible SQL Injection Attempt";
  flow:to_server,established;
  content:"' OR '1'='1"; nocase;
  http_uri;
  classtype:web-application-attack;
  sid:1000001;
  rev:1;
)
```

```
Rule Anatomy:
┌───────┬──────────────────────────────────────────────────────┐
│ action│ alert, drop, reject, pass                            │
│ proto │ tcp, udp, icmp, ip                                   │
│ src   │ $HOME_NET, any, 192.168.1.0/24                       │
│ sport │ any, 80, [1024:]                                     │
│ dir   │ -> (to dest), <> (bidirectional)                     │
│ dst   │ $EXTERNAL_NET, any                                   │
│ dport │ 80, 443, [80,443]                                    │
├───────┴──────────────────────────────────────────────────────┤
│ (options)                                                    │
│ msg:      Alert message                                      │
│ flow:     to_server/from_server, established                 │
│ content:  Pattern to match in payload                        │
│ nocase:   Case insensitive match                             │
│ http_uri: Match in HTTP URI only                             │
│ classtype: Attack category                                   │
│ sid:      Unique signature ID                                │
│ rev:      Rule revision number                               │
└──────────────────────────────────────────────────────────────┘
```

### Common Rule Examples

```
# 1. Detect nmap TCP SYN scan
alert tcp any any -> $HOME_NET any (
  msg:"NMAP TCP SYN Scan Detected";
  flags:S; threshold:type both, track by_src, count 20, seconds 5;
  classtype:attempted-recon;
  sid:1000010;
)

# 2. Detect SSH brute force
alert tcp $EXTERNAL_NET any -> $HOME_NET 22 (
  msg:"SSH Brute Force Attempt";
  flow:to_server,established;
  threshold:type threshold, track by_src, count 10, seconds 60;
  classtype:brute-force;
  sid:1000020;
)

# 3. Detect DNS query to long domain (tunneling)
alert dns any any -> any 53 (
  msg:"Potential DNS Tunneling — Long Query";
  dns_query;
  byte_test:1,>,100,0,relative;
  classtype:trojan-activity;
  sid:1000030;
)

# 4. Detect self-signed TLS certificate
alert tls any any -> any any (
  msg:"Self-Signed TLS Certificate Detected";
  tls_cert_issuer:"CN=localhost";
  classtype:policy-violation;
  sid:1000040;
)

# 5. Detect HTTP request with suspicious User-Agent
alert http $HOME_NET any -> $EXTERNAL_NET any (
  msg:"Suspicious User-Agent — Possible Tool";
  flow:to_server,established;
  http_user_agent;
  content:"sqlmap"; nocase;
  classtype:web-application-attack;
  sid:1000050;
)
```

### Testing Rules

```bash
# Test Suricata rules
suricata -T -c /etc/suricata/suricata.yaml -S custom.rules

# Test against pcap
suricata -r test.pcap -S custom.rules -l test_output/

# Check alerts generated
cat test_output/fast.log
jq 'select(.event_type=="alert")' test_output/eve.json
```


### Feature Mapping: Zeek Logs → ML Features

```
conn.log fields → ML features:
  duration      → connection_duration
  orig_bytes    → bytes_sent
  resp_bytes    → bytes_received
  orig_pkts     → packets_sent
  resp_pkts     → packets_received
  proto         → protocol (tcp=6, udp=17, icmp=1)
  service       → detected_service (categorical)
  conn_state    → connection_state (S0=scan, SF=normal, ...)

dns.log (joined on uid):
  query         → dns_query (domain name)
  qtype         → dns_query_type
  rcode         → dns_response_code
  TTLs          → dns_ttl_values
  answers       → dns_answer_count

http.log (joined on uid):
  method        → http_method
  host          → http_host
  uri           → http_uri
  status_code   → http_status
  user_agent    → http_user_agent

ssl.log (joined on uid):
  server_name   → ssl_sni
  ja3           → ssl_ja3_fingerprint
  issuer        → ssl_cert_issuer
  version       → ssl_version
```
