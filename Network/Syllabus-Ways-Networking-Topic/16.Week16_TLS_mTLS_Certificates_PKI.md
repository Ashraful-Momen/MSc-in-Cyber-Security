## 1. TLS Deep Dive

### TLS Goals (CIA + A)
```
Confidentiality:  Data encrypted — only client + server can read
Integrity:        Data cannot be modified without detection (MAC)
Authentication:   Server identity verified via certificate
Availability:     (Not TLS's job — handled by infrastructure)
```

### TLS 1.2 Full Handshake (Detailed)

```
Client                                  Server
  │                                       │
  │── (1) ClientHello ──────────────────►│
  │   - Highest TLS version supported     │
  │   - Random number (32 bytes)          │
  │   - Session ID (empty for new)        │
  │   - Cipher suites (ordered list)      │
  │     e.g., TLS_ECDHE_RSA_AES128_GCM    │
  │   - Compression methods               │
  │   - Extensions:                       │
  │     • server_name (SNI)               │ ← PLAINTEXT hostname!
  │     • supported_groups (EC curves)    │
  │     • signature_algorithms            │
  │     • ALPN (HTTP/1.1, h2)            │
  │                                       │
  │◄── (2) ServerHello ──────────────────│
  │   - Selected TLS version              │
  │   - Random number (32 bytes)          │
  │   - Session ID                        │
  │   - Selected cipher suite             │
  │   - Selected compression              │
  │   - Extensions (ALPN, etc.)            │
  │                                       │
  │◄── (3) Certificate ─────────────────│
  │   - Server's X.509 certificate        │
  │   - Full chain (server → intermediate)│
  │   - Public key                        │
  │                                       │
  │◄── (4) ServerKeyExchange ───────────│
  │   - ECDHE public key parameters       │
  │   - Signature (signed with cert key)  │
  │   (Skip if RSA key exchange)          │
  │                                       │
  │◄── (5) CertificateRequest ──────────│
  │   (Only for mTLS — optional)          │
  │                                       │
  │◄── (6) ServerHelloDone ─────────────│
  │                                       │
  │── (7) Certificate ──────────────────►│
  │   (Only for mTLS — client cert)       │
  │                                       │
  │── (8) ClientKeyExchange ───────────►│
  │   - ECDHE public key parameters       │
  │   or Pre-master secret (RSA)          │
  │                                       │
  │── (9) CertificateVerify ───────────►│
  │   (Only for mTLS)                     │
  │                                       │
  │── (10) ChangeCipherSpec ───────────►│
  │───────────────────────────────────────│
  │   FROM NOW ON: ENCRYPTED             │
  │───────────────────────────────────────│
  │── (11) Finished ───────────────────►│
  │   (Verify data — encrypted)           │
  │                                       │
  │◄── (12) ChangeCipherSpec ───────────│
  │◄── (13) Finished ───────────────────│
  │                                       │
  │◄══════ ENCRYPTED APPLICATION DATA ══►│
```

### TLS 1.3 — Simplified (1-RTT)

```
Client                                  Server
  │                                       │
  │── (1) ClientHello ──────────────────►│
  │   + Key Share (ECDHE params)          │  ← Key exchange ALREADY started!
  │   + Supported ciphers (AEAD only)     │
  │   + SNI                              │
  │                                       │
  │◄── (2) ServerHello ──────────────────│
  │   + Key Share (server ECDHE params)   │  ← Key exchange complete!
  │   {Encrypted} Certificate             │
  │   {Encrypted} CertificateVerify       │
  │   {Encrypted} Finished               │
  │                                       │
  │── (3) {Encrypted} Finished ────────►│
  │                                       │
  │◄══════ ENCRYPTED APPLICATION DATA ══►│
  │                                       │
  │ TLS 1.3 = 1 round trip (vs 2 in 1.2)  │
  │ 0-RTT mode = data sent WITH Hello!    │
```

### TLS 1.2 vs 1.3 Key Differences

```
┌───────────────────┬─────────────────────┬───────────────────────┐
│ Feature           │ TLS 1.2              │ TLS 1.3              │
├───────────────────┼─────────────────────┼───────────────────────┤
│ Handshake RTT     │ 2                    │ 1 (0-RTT possible)   │
│ Cipher Suites     │ Many (RSA, DHE, etc.)│ AEAD only (5 ciphers)│
│ Key Exchange      │ RSA or ECDHE         │ ECDHE only (PFS mandatory)│
│ RSA Key Exchange  │ Yes                  │ REMOVED (unsafe)      │
│ Renegotiation     │ Supported            │ REMOVED               │
│ Compression       │ Supported            │ REMOVED (CRIME vuln)  │
│ Static Key        │ Supported            │ REMOVED               │
│ Session Resumption│ Session ID / Tickets │ PSK-based             │
└───────────────────┴─────────────────────┴───────────────────────┘
```

### TLS Security Features

```
PFS (Perfect Forward Secrecy):
  - ECDHE key exchange = new key per session
  - Server private key compromised ≠ past sessions decryptable
  - TLS 1.3 mandates PFS → RSA key exchange removed

AEAD (Authenticated Encryption with Associated Data):
  - Encrypts AND authenticates in one operation
  - Ciphers: AES-GCM, ChaCha20-Poly1305
  - Prevents tampering + ensures confidentiality

Certificate Transparency:
  - Public logs of issued certificates
  - Browser checks: certificate MUST be logged
  - Detects mis-issued certificates
```

## 2. mTLS (Mutual TLS)

### What is mTLS?

```
Standard TLS:
  Client ──────────────────► Server
    "I want to verify SERVER is legit"
    Server presents certificate → Client verifies
    Only SERVER authenticated

mTLS:
  Client ──────────────────► Server
    "I want to verify SERVER is legit" +
    "SERVER wants to verify CLIENT is legit"
    BOTH present certificates → BOTH verified
    Client AND Server authenticated
```

### mTLS Handshake (Extra Steps)

```
Standard TLS (1-way) + these steps:

After ServerHelloDone:
  ◄── (5) CertificateRequest ─────────── Server requests client cert
  ──► (7) Client Certificate ─────────── Client sends its cert
  ──► (9) CertificateVerify ──────────── Client proves it owns private key

CertificateVerify = Client signs handshake hash with its private key
Server verifies with client's public key from certificate
→ Client IS who it claims to be
```

### mTLS Use Cases

```
1. Kubernetes Service Mesh (Istio/Linkerd)
   - Every pod has identity (SPIFFE cert)
   - Pod-to-pod communication = mTLS
   - "Service A → Service B" → mutual authentication ✓

2. Zero Trust Networking
   - No implicit trust based on network location
   - Every connection authenticated
   - "Trust nothing, verify everything"

3. API Security (B2B)
   - API provider → only authorized clients
   - Client certificate = API key (but cryptographic)

4. IoT/Mobile Device Auth
   - Device identity via certificate
   - Stronger than passwords/tokens
```

### mTLS in Practice

```bash
# curl with client certificate (mTLS)
curl --cert client.crt --key client.key \
     --cacert ca.crt \
     https://api.example.com

# Check mTLS setup
openssl s_client -connect server:443 \
  -cert client.crt -key client.key \
  -CAfile ca.crt
```

### Research Context

```
mTLS Detection + Monitoring:

1. Certificate Exchange Analysis:
   - Is client certificate sent? (mTLS indicator)
   - Certificate validity check
   - Certificate revocation status (OCSP/CRL)

2. SPIFFE Identity:
   - Kubernetes: spiffe://cluster.local/ns/default/sa/my-service
   - Monitor: unauthorized SPIFFE ID accessing service

3. mTLS Anomalies:
   - Client without certificate → possible policy bypass
   - Expired client certificate → misconfiguration/attack
   - Self-signed client cert → unauthorized client
   - Certificate reuse across services → lateral movement

4. Dataset Features:
   - mutual_auth: boolean (TLS vs mTLS)
   - client_cert_issuer, client_cert_subject
   - client_cert_validity
   - spiffe_id (Kubernetes context)
```

## 3. Certificates

### X.509 Certificate Structure

```
┌──────────────────────────────────────────────┐
│              X.509 Certificate               │
├──────────────────────────────────────────────┤
│ Version:            v3                       │
│ Serial Number:      1a:2b:3c:4d:...          │
│ Signature Algorithm: sha256WithRSAEncryption  │
│                                              │
│ Issuer:                                       │
│   CN = Let's Encrypt Authority X3            │
│   O  = Let's Encrypt                         │
│   C  = US                                    │
│                                              │
│ Validity:                                     │
│   Not Before: Jan 15 10:00:00 2024 GMT       │
│   Not After:  Apr 15 10:00:00 2024 GMT       │
│                                              │
│ Subject:                                      │
│   CN = example.com                           │
│   O  = Example Inc.                          │
│   C  = US                                    │
│                                              │
│ Subject Public Key Info:                     │
│   Algorithm: RSA (2048 bit)                  │
│   Public Key: MIIBCgKCAQEA...                │
│                                              │
│ Extensions (v3):                              │
│   Subject Alternative Name (SAN):             │
│     DNS: example.com, *.example.com          │
│   Basic Constraints: CA:FALSE                │
│   Key Usage: Digital Signature, Key Encipher │
│   Extended Key Usage: TLS Server Auth        │
│   Certificate Transparency: SCT present       │
│                                              │
│ Signature:                                    │
│   (Issuer's signature over above fields)     │
└──────────────────────────────────────────────┘
```

### Certificate Types

```
Root CA Certificate:
  - Self-signed
  - Trust anchor — must be pre-installed (OS/browser trust store)
  - Never used directly for TLS

Intermediate CA Certificate:
  - Signed by Root CA
  - Actually issues server/client certs
  - Root CA kept offline for safety

End-Entity (Leaf) Certificate:
  - Server certificate (CN = domain name)
  - Client certificate (CN = user/device identity)
  - Cannot issue other certificates (CA:FALSE)

Wildcard Certificate:
  - *.example.com → covers www.example.com, api.example.com
  - Does NOT cover sub.sub.example.com

SAN Certificate (Multi-domain):
  - Subject Alternative Names: example.com, example.net, example.org
```

### Certificate Verification

```bash
# View certificate details
openssl x509 -in cert.pem -text -noout

# Check certificate from server
openssl s_client -connect example.com:443 -showcerts

# Verify certificate chain
openssl verify -CAfile ca-bundle.crt cert.pem

# Check expiry date
openssl x509 -in cert.pem -noout -enddate

# Check if private key matches certificate
openssl x509 -noout -modulus -in cert.pem | openssl md5
openssl rsa -noout -modulus -in key.pem | openssl md5
# (Both should output same hash)

# Get certificate from remote server
echo | openssl s_client -connect example.com:443 2>/dev/null | \
  openssl x509 -noout -subject -dates
```

### Certificate Issues (Detection Features)

```
Security-relevant certificate checks:

1. Expiry:         Not After < current date → EXPIRED
2. Self-signed:    Issuer == Subject → self-signed (not trusted)
3. Weak Key:       RSA < 2048 bit → weak
4. Weak Signature: SHA-1 signature → deprecated/insecure
5. SAN Mismatch:   SNI ≠ certificate SAN entries
6. Wildcard:       *.example.com → broad scope (risk)
7. CA Trust:       Issuer in trusted store?
8. Revocation:     OCSP check → certificate revoked?
9. Extended Validation (EV): Extended org verification

ML Dataset Features from Certificate:
  cert_valid_days_remaining
  cert_is_expired (boolean)
  cert_is_self_signed (boolean)
  cert_key_size (2048, 4096)
  cert_sig_algorithm (sha256, sha1, etc.)
  cert_sni_matches_subject (boolean)
  cert_is_wildcard (boolean)
  cert_san_count
  cert_chain_length
  cert_issuer (categorical)
```

## 4. PKI (Public Key Infrastructure)

### What is PKI?
PKI = **system of roles, policies, hardware, software, and procedures** needed to create, manage, distribute, use, store, and revoke digital certificates.

```
┌──────────────────────────────────────────────────────────────┐
│                     PKI ARCHITECTURE                         │
│                                                              │
│  ┌─────────────┐      ┌──────────────┐                       │
│  │  Root CA    │─────►│ Intermediate │────► Issue certs     │
│  │ (offline)   │      │     CA       │                       │
│  └─────────────┘      └──────┬───────┘                       │
│                              │                               │
│              ┌───────────────┼───────────────┐               │
│              │               │               │               │
│         ┌────▼────┐    ┌────▼────┐    ┌────▼────┐           │
│         │ Server  │    │ Client  │    │ Code    │           │
│         │ Cert    │    │ Cert    │    │ Signing │           │
│         └─────────┘    └─────────┘    └─────────┘           │
│                                                              │
│  ┌──────────────────────────────────────────────────────┐   │
│  │ Certificate Lifecycle Management                     │   │
│  │                                                      │   │
│  │ Request → Validate → Issue → Distribute → Use        │   │
│  │                                              │        │   │
│  │                          ┌───────────────────┘        │   │
│  │                          ▼                            │   │
│  │                    Revoke (CRL / OCSP)                │   │
│  │                    Renew (before expiry)              │   │
│  │                    Expire (end of life)               │   │
│  └──────────────────────────────────────────────────────┘   │
└──────────────────────────────────────────────────────────────┘
```

### PKI Components

```
1. Certificate Authority (CA):
   Issues and signs certificates
   Trust anchor of the system

2. Registration Authority (RA):
   Verifies identity before CA issues cert
   (Often integrated with CA)

3. Certificate Revocation List (CRL):
   List of revoked certificates (periodically downloaded)
   Problem: delay between revocation and CRL update

4. OCSP (Online Certificate Status Protocol):
   Real-time certificate status check
   OCSP Stapling: server includes OCSP response → privacy + speed

5. Certificate Database:
   Stores issued certificates and their status

6. Key Management:
   Private key generation, storage, backup, destruction
   HSM (Hardware Security Module) for high-security
```

### PKI in Kubernetes

```
Kubernetes PKI Components:
```

### TLS Debugging in Kubernetes

```bash
# Check API server certificate
openssl s_client -connect k8s-api:6443 -showcerts

# Check certificate expiry
kubeadm certs check-expiration

# Check service account token
kubectl create token default -n default

# View secret TLS cert
kubectl get secret my-tls -o yaml
kubectl get secret my-tls -o jsonpath='{.data.tls\.crt}' | base64 -d | openssl x509 -text -noout

# cert-manager: check certificate status
kubectl get certificates -A
kubectl describe certificate my-cert -n my-ns
```

### Research Context

```
TLS/mTLS Dataset Features for Kubernetes Security Research:

1. TLS Session Features:
   tls_version, cipher_suite, ja3_fingerprint, sni
   handshake_duration, session_resumed (boolean)
   tls_1_3_used (boolean), is_mtls (boolean)

2. Certificate Features:
   cert_valid_days, self_signed, wildcard, key_size
   cert_issuer, cert_chain_length, is_expired
   ocsp_status (good/revoked/unknown)

3. Kubernetes-specific:
   spiffe_id, pod_identity, namespace
   cert_rotation_age, cert_manager_status
   ingress_tls_enabled, service_mesh_enabled

4. Anomaly Scenarios:
   - Pod using expired cert → misconfiguration/attack
   - Unknown CA issuer → rogue certificate
   - TLS downgrade (1.3 → 1.2) → downgrade attack
   - mTLS disabled where expected → policy violation
   - Certificate re-use across services → lateral movement

5. SHAP Explainability for TLS Features:
   "Attack classified because: JA3 fingerprint matched
    malware tool 67%, self-signed cert 23%, expired cert 10%"
```

# Self-Check Questions

1. TLS 1.2 এবং TLS 1.3 handshake-এর মধ্যে ৫টি পার্থক্য লেখ। TLS 1.3 কেন faster?
2. PFS (Perfect Forward Secrecy) কী এবং কেন important? ECDHE কীভাবে PFS provide করে?
3. TLS এবং mTLS-এর মধ্যে পার্থক্য কী? mTLS handshake-এ extra কী step থাকে?
4. X.509 certificate-এর key field গুলো কী কী? SAN (Subject Alternative Name) কেন important?
5. Certificate chain verification কীভাবে কাজ করে? Root CA, Intermediate CA, Leaf cert-এর role ব্যাখ্যা করো।
6. Certificate Revocation List (CRL) এবং OCSP-এর মধ্যে পার্থক্য কী? OCSP Stapling কী সমস্যা solve করে?
7. Kubernetes-এ TLS ব্যবহৃত হয় কোন কোন communication point-এ? (Minimum 5 examples)
8. SPIFFE ID কী? Kubernetes service mesh (Istio)-এ এটি কীভাবে ব্যবহার হয়?
9. TLS Encrypted Traffic Analysis (ETA)-এর জন্য ৮টি metadata feature list করো যা plaintext-এ visible।
10. Kubernetes cluster-এ certificate expiry monitoring setup কীভাবে করবে? Automation approach লেখ।
