## 1. Firewall Fundamentals

### সংজ্ঞা
Firewall হলো network security system যা predetermined security rules-এর ভিত্তিতে incoming/outgoing traffic monitor এবং control করে।

```
┌─────────────────────────────────────────────────────────────┐
│                     FIREWALL                                 │
│                                                              │
│    Internet ─────►│FILTER│──────► Internal Network          │
│    (Untrusted)    │RULES │        (Trusted)                  │
│                   └──────┘                                   │
│                                                              │
│    Rule: ALLOW traffic matching policy                       │
│          DENY  everything else                               │
└─────────────────────────────────────────────────────────────┘
```

### Firewall Types by Deployment

| Type | Location | Protects |
|------|----------|----------|
| **Network Firewall** | Network perimeter | Entire network |
| **Host-based Firewall** | Individual host | Single machine |
| **WAF** (Web Application Firewall) | Before web servers | HTTP/HTTPS attacks |
| **Cloud Firewall** | Cloud VPC boundary | Cloud resources |
| **Container Firewall** | Pod/Container level | Kubernetes workloads |

### Firewall Actions

```
ACCEPT  : Allow the packet through
DROP    : Silently discard (no response to sender)
REJECT  : Discard + send ICMP error back (polite refusal)
LOG     : Record packet info, then process next rule
QUEUE   : Pass to userspace application for decision
```

### Default Policy Philosophy

```
Default DENY (Whitelist approach — recommended):
  "Block everything, allow only what's needed"
  More secure, more management

Default ALLOW (Blacklist approach):
  "Allow everything, block specific threats"
  Less secure, less management
```

## 2. ACL (Access Control List)

### সংজ্ঞা
ACL হলো rules-এর ordered list যা network traffic permit বা deny করে। Traffic match করে — top-to-bottom evaluate হয়, first match-এই decision নেয়া হয়।

```
┌──────────────────────────────────────────┐
│ ACL Structure:                           │
│                                          │
│ Rule 10: ALLOW from 10.0.0.0/8 to any   │ ← First match wins!
│ Rule 20: DENY  from 192.168.1.100        │
│ Rule 30: ALLOW tcp port 443              │
│ Rule 40: ALLOW tcp port 80              │
│ Rule 50: DENY  all (implicit)            │ ← Default deny at end
└──────────────────────────────────────────┘

Traffic evaluation:
  Packet from 10.0.0.5 → Matches Rule 10 → ALLOW (stop, don't check others)
  Packet from 192.168.1.100 → Skips Rule 10 → Matches Rule 20 → DENY
  Packet from 192.168.1.50 port 443 → Skips 10,20 → Matches Rule 30 → ALLOW
```

### ACL Components

```
Each ACL entry (ACE) contains:
  ┌──────────────┬──────────────────────────────────┐
  │ Sequence #   │ Rule priority (10, 20, 30...)   │
  │ Action       │ PERMIT or DENY                   │
  │ Protocol     │ TCP, UDP, ICMP, IP               │
  │ Source IP    │ 192.168.1.0/24, any              │
  │ Source Port  │ 52341, any, gt 1024              │
  │ Dest IP      │ 10.0.0.0/8, any                  │
  │ Dest Port    │ 80, 443, range 8000-9000          │
  │ Direction    │ IN or OUT                         │
  │ Interface    │ eth0, eth1                        │
  │ State        │ NEW, ESTABLISHED, RELATED         │
  │ Log          │ Log matching packets              │
  └──────────────┴──────────────────────────────────┘
```

### iptables as ACL Implementation

```bash
# Default deny
sudo iptables -P INPUT DROP
sudo iptables -P FORWARD DROP

# Rule 10: Allow loopback (always needed)
sudo iptables -A INPUT -i lo -j ACCEPT

# Rule 20: Allow established connections (return traffic)
sudo iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT

# Rule 30: Allow SSH from specific subnet
sudo iptables -A INPUT -p tcp --dport 22 -s 192.168.1.0/24 -j ACCEPT

# Rule 40: Allow HTTP/HTTPS from anywhere
sudo iptables -A INPUT -p tcp -m multiport --dports 80,443 -j ACCEPT

# Rule 50: Allow ICMP (ping) limited
sudo iptables -A INPUT -p icmp --icmp-type echo-request \
  -m limit --limit 1/sec -j ACCEPT

# Rule 999 (implicit): Everything else DROPped by default policy

# View rules with hit counts
sudo iptables -L INPUT -n -v --line-numbers
```

### ACL Best Practices

```
1. Most specific rules FIRST
2. Default DENY policy
3. Log denied packets (for debugging/forensics)
4. Regular rule audit (remove unused rules)
5. Principle of Least Privilege (minimum access)
6. Document every rule (why it exists)
7. Version control your firewall rules
```

## 3. Stateful Firewall

### সংজ্ঞা
Stateful firewall **connection state track** করে। শুধু packet header দেখে না, connection-এর context বুঝে decision নেয়।

```
Stateful Firewall maintains CONNECTION TABLE:

┌────────────────┬──────────┬──────────┬──────────┬─────────┐
│ Source         │ Dest     │ Src Port │ Dst Port │ State    │
├────────────────┼──────────┼──────────┼──────────┼─────────┤
│ 192.168.1.5    │ 93.184.. │ 52341    │ 443      │ ESTAB   │
│ 10.0.0.3       │ 8.8.8.8  │ 61234    │ 53       │ CLOSED  │
│ ...            │ ...      │ ...      │ ...      │ ...     │
└────────────────┴──────────┴──────────┴──────────┴─────────┘

Connection States:
  NEW         : First packet of connection (SYN)
  ESTABLISHED : Connection active (双向 communication ongoing)
  RELATED     : New connection related to existing (FTP data channel)
  INVALID     : Doesn't match any tracked connection
  UNTRACKED   : Not tracked (explicitly bypassed)
```

### Why Stateful?

```
Problem with Stateless:
  Rule: ALLOW port 80 IN
  → Hacker sends packet with src port 80 → Rule matches → ALLOWED! ✗

Stateful Solution:
  Connection table tracks: client → server SYN = NEW state
  Return traffic = ESTABLISHED state (automatically allowed)
  Random packet with src port 80 = INVALID state → DROP ✓

  No need for permissive inbound rules for return traffic
```

### Stateful Firewall Example (iptables)

```bash
# Stateful rules — minimum exposure

# 1. Allow all established/related (return traffic)
iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT

# 2. Allow NEW only for specific services
iptables -A INPUT -p tcp --dport 22 -m conntrack --ctstate NEW -j ACCEPT
iptables -A INPUT -p tcp --dport 443 -m conntrack --ctstate NEW -j ACCEPT

# 3. Drop invalid packets
iptables -A INPUT -m conntrack --ctstate INVALID -j DROP

# 4. Default policy
iptables -P INPUT DROP

# This handles ALL return traffic automatically!
# No need for: "allow port 1024-65535 for return traffic"
```

### Connection Tracking Table

```bash
# View connection tracking table
sudo conntrack -L

# tcp  6 431999 ESTABLISHED src=192.168.1.5 dst=93.184.216.34
#      sport=52341 dport=443 [UNREPLIED] src=93.184.216.34 dst=192.168.1.5
#      sport=443 dport=52341 mark=0 use=1

# Count connections
sudo conntrack -C

# Count by state
sudo conntrack -S
# entries=45, searched=1234, found=1200, new=34, invalid=2, ...

# Delete specific connection
sudo conntrack -D -p tcp --orig-port-src 52341
```

### Research Context
- Connection tracking table → flow feature source
- NEW connection rate → DoS indicator
- INVALID packet rate → scan/spoof indicator
- Kubernetes kube-proxy heavily uses conntrack

## 4. Stateless Firewall

### সংজ্ঞা
Stateless firewall প্রতিটি packet individually evaluate করে — connection context maintain করে না। শুধু packet header-এর current information দেখে।

```
Stateless Firewall Decision:
  "Source IP = 192.168.1.5? Dest Port = 80? Protocol = TCP? → ALLOW"
  (Doesn't know or care if this is part of existing connection)

Stateful Firewall Decision:
  "Source IP = 192.168.1.5, Dest Port = 80, Protocol = TCP,
   AND this packet belongs to existing connection #4532 → ALLOW"
  (Knows the connection history)
```

### Stateless vs Stateful

```
┌─────────────────┬──────────────────────┬──────────────────────┐
│ Feature         │ Stateless            │ Stateful              │
├─────────────────┼──────────────────────┼──────────────────────┤
│ Memory          │ Packet only          │ Connection table      │
│ Speed           │ Faster (no table)    │ Slightly slower       │
│ Resource Use    │ Low memory           │ Higher memory          │
│ Security        │ Weaker               │ Stronger              │
│ Return Traffic  │ Need explicit rules  │ Automatic (related)   │
│ Attack Defense  │ Basic                │ Good (state check)    │
│ Use Case        │ Core routers, ACL    │ Host/network firewall │
│ Modern?         │ Legacy               │ Standard              │
└─────────────────┴──────────────────────┴──────────────────────┘
```

### Stateless Example

```bash
# Stateless rules (careful — return traffic needs explicit rules!)

# Allow incoming HTTP request
iptables -A INPUT -p tcp --dport 80 -j ACCEPT

# But ALSO need to allow HTTP response to go out:
iptables -A OUTPUT -p tcp --sport 80 -j ACCEPT

# AND client-side ephemeral ports for return traffic:
iptables -A INPUT -p tcp --dport 1024:65535 -j ACCEPT  ← WEAK!
# (This opens huge range — bad security practice)

# Stateful solves this with ONE rule:
iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
```

## 5. Firewall in Kubernetes Context

### Kubernetes Network Security Layers

```
┌─────────────────────────────────────────────────────────────┐
│                   KUBERNETES FIREWALL LAYERS                 │
│                                                              │
│  L1: Node-level Firewall                                     │
│      iptables/nftables on each node                          │
│      Control plane protection (API server, etcd)             │
│                                                              │
│  L2: Network Policy (Kubernetes native)                      │
│      Pod-to-pod traffic control                              │
│      Namespace isolation                                     │
│      Implemented by CNI (Calico, Cilium)                     │
│                                                              │
│  L3: Cloud Firewall (Security Groups / NACL)                 │
│      AWS Security Groups, GCP Firewall Rules                  │
│      Node communication, load balancer access                 │
│                                                              │
│  L4: Service Mesh (Istio/Linkerd)                            │
│      L7 policies (HTTP path, header, method)                 │
│      mTLS enforcement                                         │
│      AuthorizationPolicy                                     │
└─────────────────────────────────────────────────────────────┘
```

### Network Policy Example

```yaml
# Kubernetes NetworkPolicy = Stateful ACL for Pods
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: api-allow
spec:
  podSelector:
    matchLabels:
      app: api-server
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: frontend     # Allow ONLY from frontend pods
    ports:
    - protocol: TCP
      port: 8080            # On port 8080 only
  # Default deny for everything else (implicit)
```

### Research Connection

```
Firewall → Dataset Features & Monitoring:

1. ACL Hit Counts:
   iptables -L -n -v → per-rule packet/byte counters
   → Time-series: rule hit rate changes → anomaly

2. Connection Tracking:
   conntrack -S → connection state distribution
   → NEW rate spike → scan/attack

3. DROP/REJECT Logs:
   iptables -A INPUT -j LOG --log-prefix "FIREWALL-DROP: "
   → dmesg | grep FIREWALL → blocked traffic patterns

4. Network Policy Events:
   Kubernetes audit logs → when policies change
   → Unexpected policy changes → security incident

5. Abnormal State Distribution:
   High INVALID state → spoofing/scanning
   High NEW without ESTABLISHED growth → SYN flood
```
