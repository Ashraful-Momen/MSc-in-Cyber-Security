## 1. Security Group

### What is Security Group?
Security Group = **stateful virtual firewall** for cloud resources (EC2, RDS, ELB, EKS nodes)। Instance-level security.

```
┌──────────────────────────────────────────────────────┐
│                 SECURITY GROUP                       │
│                                                      │
│  Acts at:    Instance/Resource level                 │
│  State:      STATEFUL (return traffic auto-allowed)  │
│  Rules:      ALLOW only (no DENY rules)              │
│  Default:    Deny all inbound, Allow all outbound    │
│  Evaluation: All rules evaluated (most permissive)   │
│                                                      │
│  ┌────────────────────────────────────────────────┐  │
│  │  Inbound Rules                                 │  │
│  │  Type    Proto  Port    Source                  │  │
│  │  ────────────────────────────────────────────── │  │
│  │  SSH     TCP    22      192.168.1.0/24          │  │
│  │  HTTP    TCP    80      0.0.0.0/0               │  │
│  │  HTTPS   TCP    443     0.0.0.0/0               │  │
│  │  Custom  TCP    8080    sg-app-server           │  │
│  │                              └── Reference!     │  │
│  └────────────────────────────────────────────────┘  │
│                                                      │
│  ┌────────────────────────────────────────────────┐  │
│  │  Outbound Rules (default: ALLOW ALL)           │  │
│  │  Type    Proto  Port    Destination            │  │
│  │  ────────────────────────────────────────────── │  │
│  │  ALL     ALL    ALL     0.0.0.0/0              │  │
│  └────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────┘
```

### Security Group Features

```
1. Stateful:
   Inbound rule: Allow port 80 in
   → Outbound response traffic automatically allowed
   → No need for explicit outbound rule for responses

2. Allow rules ONLY:
   Can't create DENY rules
   What you don't allow → automatically denied
   Simpler, but less flexible than NACL

3. Source can be:
   - CIDR block: 192.168.1.0/24
   - Security Group ID: sg-12345678
   - Anywhere: 0.0.0.0/0 (IPv4), ::/0 (IPv6)

4. Apply to:
   - Multiple instances (one SG → many instances)
   - Multiple SGs per instance (up to 5 typically)

5. Changes take effect IMMEDIATELY
```

### Security Group Best Practices

```
┌──────────────────────────────────────────────────────────────┐
│              SECURITY GROUP TIERING                           │
│                                                               │
│  sg-bastion:      SSH (22) from office IP only               │
│  sg-loadbalancer: HTTP (80), HTTPS (443) from 0.0.0.0/0     │
│  sg-app-server:   HTTP (8080) from sg-loadbalancer           │
│                   SSH (22) from sg-bastion                   │
│  sg-database:     MySQL (3306) from sg-app-server            │
│                   SSH (22) from sg-bastion                   │
│                                                               │
│  Principle of Least Privilege:                                │
│  App server only talks to DB on 3306 —                       │
│  not to other DBs, not to internet (unless needed)           │
└──────────────────────────────────────────────────────────────┘
```

### Kubernetes Node Security Groups

```
EKS Node Security Group:

Inbound:
  - TCP 443 from kube-apiserver (control plane SG)
  - TCP 10250 from control plane (kubelet API)
  - TCP 30000-32767 from sg-loadbalancer (NodePort range)
  - UDP 4789 from other node SGs (VXLAN / pod networking)
  - TCP 443, 10250 from other node SGs (inter-node)

Outbound:
  - ALL to 0.0.0.0/0 (nodes need internet for images, updates)
  - Or restrict to: VPC CIDR + specific internet endpoints

Pod networking:
  - If AWS VPC CNI: pod IPs are VPC IPs → SG applies to pods too!
  - If Calico/Cilium overlay: pod traffic encapsulated → node SG
```

## 2. Network ACL (NACL)

### What is NACL?
NACL = **stateless firewall** at the **subnet level**। Subnet-এ enter/exit হওয়া সব traffic NACL rules-এর মাধ্যমে যায়।

```
┌──────────────────────────────────────────────────────┐
│                   NETWORK ACL                        │
│                                                      │
│  Acts at:    Subnet level                            │
│  State:      STATELESS (must explicitly allow both   │
│              inbound + outbound for return traffic)   │
│  Rules:      ALLOW + DENY                            │
│  Default:    Allow all (default NACL)                 │
│  Evaluation: Rule number order (lowest first match)  │
│                                                      │
│  ┌────────────────────────────────────────────────┐  │
│  │  Inbound Rules (Rule # → evaluated in order)   │  │
│  │  #     Type   Proto  Port    Source      Action │  │
│  │  ────────────────────────────────────────────── │  │
│  │  100   HTTP   TCP    80      0.0.0.0/0   ALLOW │  │
│  │  200   HTTPS  TCP    443     0.0.0.0/0   ALLOW │  │
│  │  300   SSH    TCP    22      10.0.0.0/8  ALLOW │  │
│  │  *     ALL    ALL    ALL     0.0.0.0/0   DENY  │  │ ← Default rule
│  └────────────────────────────────────────────────┘  │
│                                                      │
│  ┌────────────────────────────────────────────────┐  │
│  │  Outbound Rules (for return traffic!)           │  │
│  │  #     Type   Proto  Port    Dest        Action │  │
│  │  ────────────────────────────────────────────── │  │
│  │  100   ALL    ALL    ALL     0.0.0.0/0   ALLOW │  │
│  └────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────┘
```

### NACL Stateless — Critical Understanding

```
Because NACL is STATELESS, return traffic needs EXPLICIT outbound rule:

Client → Server:  INBOUND Rule #100: ALLOW TCP 80 from 0.0.0.0/0
Server → Client:  OUTBOUND Rule must also allow TCP from port 80 to ephemeral ports

Without outbound rule → response blocked → connection fails even though inbound allowed!

Ephemeral Port Range (varies by OS):
  Linux:   32768-60999
  Windows: 49152-65535
  AWS NACL: can allow 1024-65535 for return

This is why Security Groups (stateful) are easier for most use cases!
```

### NACL Use Cases

```
1. Defense in Depth (SG + NACL):
   SG allows port 80, NACL blocks specific malicious IPs
   → Even if SG allows, NACL can DENY

2. Subnet-Level Blocking:
   Block entire subnet from internet (even if someone adds public IP)
   → NACL deny inbound 0.0.0.0/0 prevents all internet access

3. Protocol-Level Blocking (e.g., Block ICMP):
   NACL deny ICMP to entire subnet
   → No device in subnet responds to ping

4. Blacklisting IPs:
   NACL rule #50: DENY 203.0.113.0/24
   → While SG allows (no deny support), NACL blocks specific IPs
```

## 3. Security Group vs NACL

```
┌──────────────────┬──────────────────────┬─────────────────────┐
│ Feature          │ Security Group       │ Network ACL         │
├──────────────────┼──────────────────────┼─────────────────────┤
│ Scope            │ Instance/Resource    │ Subnet              │
│ State            │ STATEFUL             │ STATELESS           │
│ Rule Type        │ ALLOW only           │ ALLOW + DENY        │
│ Rule Evaluation  │ All rules evaluated  │ Ordered by rule #   │
│ Return Traffic   │ Automatic            │ Explicit rule needed│
│ Apply To         │ Attached to instance │ Subnet association  │
│ Default          │ Deny all inbound     │ Allow all (default) │
│ Layer            │ L3/L4                │ L3/L4               │
│ Logging          │ VPC Flow Logs        │ VPC Flow Logs       │
└──────────────────┴──────────────────────┴─────────────────────┘

Best Practice:
  SG = primary firewall (instance level, stateful, easier)
  NACL = additional layer (subnet level, stateless, DENY capability)
  Use BOTH for defense-in-depth
```

## 4. Load Balancer

### Load Balancer Types

```
┌──────────────────────────────────────────────────────────────────┐
│                      LOAD BALANCER TYPES                         │
│                                                                  │
│  L4 Load Balancer (Network LB / NLB):                           │
│  ┌────────────────────────────────────────────────────────────┐ │
│  │ Works at:   L4 (TCP/UDP)                                  │ │
│  │ Decision:   IP + Port (5-tuple hash)                      │ │
│  │ Performance: Very high (millions RPS)                     │ │
│  │ Protocol:   TCP, UDP, TLS                                  │ │
│  │ IP:         Static IP                                      │ │
│  │ Health:     TCP handshake only                             │ │
│  │ Use:        High throughput, static IP, non-HTTP          │ │
│  └────────────────────────────────────────────────────────────┘ │
│                                                                  │
│  L7 Load Balancer (Application LB / ALB):                       │
│  ┌────────────────────────────────────────────────────────────┐ │
│  │ Works at:   L7 (HTTP/HTTPS)                               │ │
│  │ Decision:   URL path, Host header, headers, query params  │ │
│  │ Performance: Medium (thousands RPS)                       │ │
│  │ Protocol:   HTTP, HTTPS, gRPC, WebSocket                  │ │
│  │ IP:         Dynamic (resolves to changing IPs)            │ │
│  │ Health:     HTTP health check endpoint                     │ │
│  │ Features:   SSL termination, redirect, auth, WAF            │ │
│  │ Use:        Web apps, microservices, API gateway          │ │
│  └────────────────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────────────────┘
```

### Load Balancer Architecture

```
                    ┌──────────────┐
    Internet ──────►│ Load Balancer│
                    │ (Public IP)  │
                    └──────┬───────┘
                           │
              ┌────────────┼────────────┐
              │            │            │
         ┌────▼───┐   ┌───▼────┐   ┌───▼────┐
         │Target 1│   │Target 2│   │Target 3│
         │Healthy │   │Healthy │   │Unhealthy│ ← Health check
         │  ✓     │   │  ✓     │   │   ✗     │    removes from
         └────────┘   └────────┘   └────────┘    rotation

Target Group: Backend servers (EC2, containers, pods)
Health Check: Periodic test → unhealthy → stop sending traffic
Listener:     Frontend port + protocol → Target Group
```

### L7 Load Balancer Routing Rules

```
Listener: Port 443 (HTTPS)
  ↓
Rules (evaluated in order — first match wins):

Rule 1: Host = api.example.com, Path = /users*    → Target Group: users-svc
Rule 2: Host = api.example.com, Path = /orders*   → Target Group: orders-svc
Rule 3: Host = api.example.com, Path = /payments* → Target Group: payments-svc
Rule 4: Host = *.admin.example.com               → Target Group: admin-svc
Rule 5: Default rule                              → Target Group: default-svc

This is how one ALB can route to multiple microservices!
```

### Kubernetes + Cloud Load Balancer

```
Kubernetes Service Type: LoadBalancer

apiVersion: v1
kind: Service
metadata:
  name: my-app
spec:
  type: LoadBalancer
  ports:
  - port: 80
    targetPort: 8080
  selector:
    app: my-app

What happens:
1. kubectl apply → Cloud Controller detects Service type: LoadBalancer
2. Cloud Controller → Creates cloud LB (AWS NLB/ALB, GCP LB, etc.)
3. LB receives Public IP / DNS
4. LB → NodePort → Pod (kubernetes internal routing)
5. Health check → pod readiness probe

Ingress Controller (L7):
  Ingress → ALB (AWS Load Balancer Controller) → Services → Pods
  More features, more control, path-based routing
```

### Research Context

```
Load Balancer Access Logs → Security Dataset:

Fields:
  timestamp, client_ip, lb_ip, backend_ip, request_processing_time
  backend_processing_time, response_processing_time
  elb_status_code, backend_status_code
  received_bytes, sent_bytes
  request_method, url, user_agent

ML Features:
  - Request rate per client IP (DDoS detection)
  - Error rate (4xx/5xx ratio)
  - Backend response time (anomaly)
  - Request path diversity (scan detection)
  - Geo-distribution of client IPs
```

# Self-Check Questions

1. Security Group এবং NACL-এর মধ্যে ৬টি পার্থক্য লেখ। Defense-in-depth architecture-এ কীভাবে দুটোই use করা হয়?
2. Security Group stateless হলে কী সমস্যা হতো? Stateful হওয়ার advantage কী?
3. NACL outbound ephemeral port range allow না করলে কী সমস্যা হবে? এটি Security Group-এ কেন ঘটে না?
4. L4 (NLB) এবং L7 (ALB) Load Balancer-এর মধ্যে পার্থক্য কী? Kubernetes-এ কোনটা কখন use করবে?
5. ALB path-based routing কীভাবে microservices architecture-এ সাহায্য করে? উদাহরণ দাও।
6. Security Group-এ source হিসেবে অন্য Security Group ID দিলে কী advantage? CIDR দিলে কী limitation?
7. Kubernetes Service `type: LoadBalancer` create করলে cloud-এ কী ঘটে? Controller-এর role কী?
8. NACL-এ rule number ordering কেন important? Rule 100 (ALLOW) এবং Rule 200 (DENY) — কোনটা কার্যকর হবে?
9. Load Balancer health check কী? Kubernetes pod readiness probe-এর সাথে এর সম্পর্ক কী?
10. Cloud LB access logs থেকে attack detection-এর জন্য ৮টি ML feature list করো।
