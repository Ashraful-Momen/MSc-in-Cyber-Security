# OSI Model: বাস্তব সিস্টেম কীভাবে কাজ করে (ধাপে ধাপে)

## পরিস্থিতি

তোমার laptop Wi-Fi-তে যুক্ত। ব্রাউজারে লিখলে `https://example.com/login`। এই একটা কাজ শুরু থেকে শেষ পর্যন্ত প্রতিটি layer-এ কী ঘটে, সেটাই এখানে এক গল্পের মতো ধরা হলো।

ধরে নিচ্ছি:
- তোমার IP `192.168.1.10`, MAC `AA:AA:AA:AA:AA:AA`
- Router (default gateway) IP `192.168.1.1`, MAC `BB:BB:BB:BB:BB:BB`
- Server IP `93.184.216.34`, port 443

## আগে একটা বাস্তব সত্য

OSI ৭ layer **তাত্ত্বিক মডেল**। Real OS-এ ভাগটা এরকম:

| অংশ | কোথায় চলে |
|---|---|
| L7 (HTTP), L6 (TLS), L5 (session logic) | **User space**: ব্রাউজার ও library (OpenSSL, NSS, BoringSSL) |
| L4 (TCP/UDP), L3 (IP) | **Kernel**: OS-এর network stack |
| L2 (MAC) | Kernel driver + **NIC hardware** |
| L1 (PHY) | NIC-এর PHY chip, cable, radio |

User space আর kernel-এর সীমানা হলো **Socket API**। ব্রাউজার `send()` কল করলে ডেটা kernel-এ ঢোকে, তারপর L4 থেকে নিচের কাজ kernel আর hardware করে। আলাদা "Session layer" TCP/IP-তে নেই। সেই কাজ TLS আর application নিজেই করে।

## ধাপ ১: Application Layer (L7), URL থেকে ঠিকানা

ব্রাউজার URL ভাঙে: scheme = `https`, host = `example.com`, path = `/login`। scheme থেকে সে জানে default port 443।

ব্রাউজারের কাছে শুধু নাম আছে, IP নেই। তাই সে OS-এর resolver (`getaddrinfo`) কে জিজ্ঞেস করে। Resolver ক্রম অনুযায়ী দেখে: browser DNS cache, OS cache, hosts file, তারপর configured DNS server (ধরো router `192.168.1.1` বা `8.8.8.8`)।

DNS query আসলে **নিজেই একটা পুরো network ট্রিপ**। এটা সাধারণত **UDP, port 53**-এ যায়। Query-তে থাকে Transaction ID (16 bit), প্রশ্ন (`example.com`, type A/AAAA)। Response বড় হলে (DNSSEC, EDNS) বা truncated হলে TCP-তে fallback হয়। DoH বা DoT হলে DNS নিজেই TLS-এর ভেতরে যায়।

এই DNS query নিচের ধাপ ৩ থেকে ৭-এর মতোই সব layer পার হয়, শুধু UDP দিয়ে। তাই আগে মূল flow বুঝে নাও।

**Security দৃষ্টিকোণ:** Transaction ID ও source port predict করা গেলে DNS cache poisoning (Kaminsky attack) সম্ভব। DNSSEC এর প্রতিরক্ষা।

## ধাপ ২: Socket তৈরি (L4-এর প্রবেশদ্বার)

IP পাওয়ার পর ব্রাউজার kernel-কে বলে:

```c
fd = socket(AF_INET, SOCK_STREAM, 0);   // TCP socket
connect(fd, 93.184.216.34:443);
```

`socket()` kernel-এ একটা **file descriptor** আর একটা internal structure বানায়। তাতে এখনো IP/port বসেনি। `connect()` কল হলে kernel:

1. **Ephemeral source port** বাছে (সাধারণত 32768–60999 Linux-এ, 49152–65535 IANA)। ধরো `51234`।
2. **Routing table** দেখে কোন interface আর কোন source IP ব্যবহার হবে।
3. এখন connection-এর পরিচয় তৈরি হলো, **5-tuple**:

```
(TCP, 192.168.1.10, 51234, 93.184.216.34, 443)
```

Server-এ হাজার client একই port 443-এ আসতে পারে, কারণ প্রতিটির 5-tuple আলাদা। Kernel এই tuple ধরে hash table-এ lookup করে ঠিক socket খুঁজে নেয়।

## ধাপ ৩: Layer 4, TCP Three-Way Handshake

`connect()` kernel-কে TCP state machine চালু করায়। সে **SYN segment** বানায়:

```
Src Port 51234 | Dst Port 443
Sequence Number = ISN (random 32-bit, ধরো 1000)
Flags = SYN
Window Size
Options: MSS=1460, Window Scale, SACK-permitted, Timestamps
Checksum
```

- **ISN random** কেন: predictable হলে attacker sequence guess করে connection hijack বা spoof করতে পারে।
- **MSS option:** "আমি এক segment-এ সর্বোচ্চ 1460 byte payload নিতে পারি।" MTU 1500 থেকে IP (20) ও TCP (20) header বাদ দিলে এটা আসে।
- Checksum **pseudo-header** (src/dst IP, protocol, length) সহ গণনা হয়, তাই IP বদলালে checksum ভুল হয়।

State: `CLOSED → SYN_SENT`। **Retransmission timer** চালু হয়, জবাব না এলে আবার SYN পাঠায়।

এই segment এখন নিচে যায়। এই প্রথম SYN packet কীভাবে wire পর্যন্ত পৌঁছায়, সেটাই পরের ধাপ।

## ধাপ ৪: Layer 3, IP Packet বানানো ও Routing সিদ্ধান্ত

Kernel segment-কে IP header-এর ভেতরে মোড়ে:

```
Version=4 | IHL | DSCP | Total Length
Identification | Flags (DF=1) | Fragment Offset
TTL=64 | Protocol=6 (TCP) | Header Checksum
Src IP = 192.168.1.10
Dst IP = 93.184.216.34
```

- **Protocol=6** মানে payload-এ TCP আছে। গ্রহণকারী এটা দেখে ঠিক upper protocol-এ পাঠায় (UDP=17, ICMP=1)।
- **TTL** প্রতিটি router-এ ১ কমে। 0 হলে packet ফেলে দিয়ে ICMP "Time Exceeded" যায়। এটাই traceroute-এর ভিত্তি।
- **DF=1:** TCP সাধারণত Don't Fragment সেট করে।

**Routing decision (longest prefix match):** Kernel routing table দেখে। `93.184.216.34` তোমার subnet `192.168.1.0/24`-এর মধ্যে নয়। তাই match হয় `default via 192.168.1.1`। অর্থাৎ **next hop = gateway**। Destination IP বদলায় না, কিন্তু frame পাঠানো হবে gateway-র কাছে।

---

## ধাপ ৫: Layer 2, ARP ও Frame বানানো

Frame বানাতে **next hop-এর MAC** দরকার। Kernel ARP cache-এ `192.168.1.1` খোঁজে। না থাকলে **ARP Request** broadcast করে:

```
Ethernet: Dst = FF:FF:FF:FF:FF:FF, EtherType = 0x0806
ARP: "Who has 192.168.1.1? Tell 192.168.1.10"
```

Router unicast উত্তর দেয়: "192.168.1.1 is at BB:BB:BB:BB:BB:BB"। কাজ শেষে MAC cache হয়।

**ARP-এর কোনো authentication নেই**, তাই ARP spoofing / MITM সম্ভব। এটা L2 attack-এর ভিত্তি।

এবার **Ethernet frame** পূর্ণ হয়:

```
Dst MAC  = BB:BB:BB:BB:BB:BB   (gateway, server নয়!)
Src MAC  = AA:AA:AA:AA:AA:AA
EtherType= 0x0800 (IPv4)
[ IP packet ]
FCS (CRC-32, 4 byte) trailer
```

- **EtherType** জানায় ভেতরে কী: IPv4 `0x0800`, IPv6 `0x86DD`, ARP `0x0806`, VLAN `0x8100`।
- **FCS** হলো error **detection** (correction নয়)। গ্রহণকারী CRC মেলাতে না পারলে frame নিঃশব্দে ফেলে দেয়।
- Header 14 byte + FCS 4 byte। MTU 1500 হলে max frame 1518 byte।

### Wi-Fi হলে বাড়তি যা ঘটে
Frame আসলে **802.11 frame** হয়, যাতে **৩-৪টা address** থাকে (STA, AP, final destination)। Medium shared, তাই **CSMA/CA**: আগে শোনো, ফাঁকা থাকলে backoff করে পাঠাও। প্রতিটি unicast frame-এর পর receiver L2 **ACK** পাঠায়। WPA2/WPA3 L2-তেই frame encrypt করে (CCMP/GCMP), অর্থাৎ air-এ তোমার data আগেই এক দফা encrypted।

## ধাপ ৬: Layer 1, Bit থেকে Signal

NIC-এর MAC hardware frame-কে **DMA** দিয়ে memory থেকে নেয়। তার সামনে **Preamble (7 byte) + SFD (1 byte)** জোড়ে (receiver-এর clock sync-এর জন্য)। দুই frame-এর মাঝে **Inter-Frame Gap (12 byte সময়)** রাখা হয়।

PHY এই bit-কে signal-এ রূপ দেয়:
- Copper: voltage level (Gigabit Ethernet-এ PAM-5 encoding)
- Fiber: আলোর pulse
- Wi-Fi: OFDM modulation দিয়ে radio wave

**এই প্রথম layer যেখানে "Bits" বলা যায়।** Frame কখনো আলাদা করে "bit হয়ে যায়" না। Frame-ই bit-এর stream হিসেবে signal আকারে যায়।

## ধাপ ৭: পথে প্রতিটি Device কী করে

### Access Point / Switch (L2 device)
Switch frame-এর **Dst MAC** পড়ে, **MAC address table** দেখে কোন port-এ পাঠাবে। Source MAC দেখে টেবিল **শিখে** (learning)। Dst MAC অজানা হলে সব port-এ flood করে। **IP পড়ে না।**
*Attack: MAC flooding দিয়ে table ভরে switch-কে hub বানানো।*

### Home Router / Gateway (L3 device)
1. Frame পায়, Dst MAC নিজের কিনা দেখে, FCS যাচাই করে।
2. **Ethernet header ও trailer খুলে ফেলে** (decapsulation)। ভেতরে IP packet।
3. IP checksum ঠিক আছে কিনা দেখে, **TTL ১ কমায়**, checksum আবার গণনা করে।
4. **NAT:** Source IP `192.168.1.10` বদলে সে নিজের public IP বসায়, source port-ও বদলায়। এই mapping **conntrack table**-এ রাখে যাতে উত্তর ফেরার সময় উল্টে দিতে পারে। TCP checksum-ও পুনর্গণনা হয়।
5. Routing table দেখে next hop (ISP router) ঠিক করে, নতুন **ARP/L2 header** বানায়: Src MAC = router-এর WAN MAC, Dst MAC = ISP router-এর MAC।
6. নতুন frame পাঠায়।

**মূল কথা:** প্রতিটি router-এ **L2 header নতুন করে তৈরি হয়**। Src/Dst MAC প্রতি hop-এ বদলায়, কিন্তু **Dst IP পুরো পথে একই** (NAT-এ Src IP একবার বদলায়)।

ISP থেকে server পর্যন্ত আরও ১০-২০টি router পার হয়। **BGP** ঠিক করে কোন AS-এর ভেতর দিয়ে যাবে, ভেতরে OSPF/IS-IS। প্রতিটি hop একই কাজ করে: frame খোলো, IP দেখো, TTL কমাও, নতুন frame বানাও।

**Fragmentation কোথায়:** পথে কোনো link-এর MTU ছোট হলে এবং packet-এ DF=1 থাকলে router packet ফেলে দিয়ে ICMP "Fragmentation Needed (Type 3 Code 4)" পাঠায়। এটা **Path MTU Discovery**। কেউ ICMP block করলে "PMTU black hole" হয়, connection ঝুলে যায়।

## ধাপ ৮: Server-এর দিকে উপরে ওঠা (Decapsulation)

Server-এর NIC frame পেয়ে একে একে:

1. **L2:** FCS ঠিক কিনা, Dst MAC নিজের কিনা। EtherType `0x0800` দেখে header খুলে IP stack-এ দেয়।
2. **L3:** IP checksum, Dst IP নিজের কিনা। **Fragment হলে** এখানে অপেক্ষা করে, সব টুকরো এলে reassemble করে (reassembly **শুধু final destination-এ**)। Protocol=6 দেখে TCP-তে দেয়।
3. **L4:** TCP checksum যাচাই। 5-tuple দিয়ে socket খোঁজে। কোনো established connection নেই, কিন্তু port 443-এ **LISTEN socket** আছে। Flag SYN, তাই নতুন connection শুরু।

Server-এর kernel তখন **SYN queue**-তে entry রাখে, state `SYN_RECEIVED`, আর পাঠায় **SYN+ACK**:

```
Seq = 5000 (server ISN), Ack = 1001 (client ISN+1)
Flags = SYN, ACK
Options: MSS, Window Scale ...
```

এই SYN+ACK একই পথে উল্টো দিকে আসে (NAT-এর conntrack entry দেখে router ঠিক laptop-কে পাঠায়)। Client পাঠায় **ACK** (Seq=1001, Ack=5001)। Client-এ state `ESTABLISHED`। Server ACK পেলে entry **accept queue**-তে সরে, আর application-এর `accept()` কল তখন **নতুন connected socket** পায়। Listening socket চলতেই থাকে।

**SYN flood:** attacker শুধু SYN পাঠিয়ে ACK দেয় না, SYN queue ভরে যায়। প্রতিরক্ষা **SYN cookies**: state না রেখে ISN-এর ভেতরেই তথ্য encode করে, ACK ফেরত এলে তবে state তৈরি হয়।

## ধাপ ৯: TLS Handshake (L6 / L5-এর কাজ)

TCP connection এখন শুধু **কাঁচা byte-এর নল**। এতে কোনো encryption নেই। ব্রাউজার TLS library-কে বলে handshake চালাতে। TLS 1.3-এ ক্রম:

**১. ClientHello (plaintext)**
- supported TLS versions, cipher suites (যেমন `TLS_AES_128_GCM_SHA256`)
- **key_share:** ECDHE-এর জন্য client-এর public key (ধরো X25519)
- **SNI:** `example.com` (কোন site চাই, **plaintext, ECH না থাকলে**)
- **ALPN:** `h2, http/1.1` (কোন application protocol)
- random (32 byte)

**২. ServerHello (plaintext)** শুধু বেছে নেওয়া cipher ও server-এর key_share।

এই মুহূর্তে দুই পক্ষ ECDHE দিয়ে একই **shared secret** বের করে ফেলে। Key কখনো wire দিয়ে যায়নি। সেই secret থেকে **HKDF** দিয়ে handshake traffic key তৈরি হয়। এরপর সব কিছু **encrypted**।

**৩. Server-এর encrypted বার্তা:**
- `EncryptedExtensions`
- `Certificate` (leaf → intermediate chain)
- `CertificateVerify` (server-এর private key দিয়ে handshake transcript-এর signature, প্রমাণ যে সে certificate-এর আসল মালিক)
- `Finished` (পুরো handshake-এর MAC)

**৪. Client যাচাই করে:**
- Chain **trusted root CA**-তে পৌঁছায় কিনা (OS/browser trust store)
- Hostname certificate-এর **SAN**-এর সাথে মেলে কিনা
- Expiry, revocation (OCSP stapling/CRL), Certificate Transparency
- `CertificateVerify` ও `Finished` ঠিক কিনা

**৫. Client `Finished` পাঠায়।** এরপর দুই পক্ষ **application traffic key** নিয়ে কাজ শুরু করে।

**ফল:** Confidentiality, Integrity, Server Authentication, **Forward Secrecy** (ephemeral key ফেলে দেওয়া হয়, তাই পরে server private key চুরি গেলেও পুরনো traffic পড়া যায় না)।

**TLS 1.2-এর পার্থক্য:** ২ round-trip, ChangeCipherSpec message, আর RSA key exchange হলে forward secrecy থাকে না।

**TLS Session এখানেই:** TLS-এর "session" মানে এই handshake-এর ফলে তৈরি crypto state। Server `NewSessionTicket` পাঠায়। পরের বার ticket/PSK দিয়ে **resumption** করলে full handshake লাগে না। TLS 1.3-এ **0-RTT** আছে, কিন্তু সেই data **replay করা যায়**, তাই শুধু idempotent request-এ ব্যবহার উচিত।

**TLS Record Layer:** প্রতিটি data টুকরো **সর্বোচ্চ 16 KB (2¹⁴)** plaintext নিয়ে একটা record:

```
Record header (5 byte): type=23 (application_data), version, length
Encrypted: [plaintext | inner content type | padding] + 16 byte AEAD tag
```

Nonce হয় sequence number থেকে। এজন্য record reorder/drop করলে decrypt ব্যর্থ হয়।

## ধাপ ১০: Application Data, HTTP Request ও Session Handling

TLS চালু। ব্রাউজার HTTP request লেখে (ALPN `h2` হলে HTTP/2 binary frame, নইলে text):

```
GET /login HTTP/1.1
Host: example.com
User-Agent: ...
Cookie: sid=...      (আগে login করা থাকলে)
```

### তিন ধরনের "Session", গুলিয়ে ফেলা চলবে না

| স্তর | কী | কতক্ষণ থাকে |
|---|---|---|
| **TCP connection** (L4) | 5-tuple, seq/ack state, window | SYN থেকে FIN/RST |
| **TLS session** (L5/6) | key, cipher, ticket | handshake থেকে close/ticket expiry |
| **Application session** (L7) | login state, cart, user identity | server-এর নিয়ম অনুযায়ী (মিনিট থেকে দিন) |

HTTP নিজে **stateless**। প্রতিটি request আলাদা। তাই login-এর পর server random **Session ID** বানায়, নিজের memory/Redis/DB-তে সেই ID-র সাথে user-এর state রাখে, আর পাঠায়:

```
Set-Cookie: sid=9f3a...; Secure; HttpOnly; SameSite=Lax
```

Browser পরের প্রতিটি request-এ এই cookie পাঠায়। অন্য উপায়: **JWT** (server state রাখে না, token নিজেই signed claim)।
`Secure` = শুধু HTTPS-এ, `HttpOnly` = JavaScript পড়তে পারবে না (XSS থেকে বাঁচায়), `SameSite` = CSRF কমায়।

**Attack:** Session hijacking (XSS বা sniffing-এ token চুরি), **Session fixation** (login-এর আগেই attacker-এর ID চাপানো, প্রতিরক্ষা: login-এ ID regenerate), replay, CSRF। এসবই L7 session attack। TCP hijack আলাদা, সেটা L4।

---

## ধাপ ১১: এই request নিচে নামার সময় Data-র রূপ বদল (Encapsulation-এর পুরো ছবি)

ধরো POST-এ 3000 byte HTTP data পাঠাচ্ছো:

```
L7  HTTP message, 3000 byte                           → Data
L6  TLS record: encrypt + 5 byte header + 16 byte tag → TLS Record (~3021 byte)
L5  (আলাদা PDU নেই, TLS/app নিজেই handle করে)
L4  TCP stream-কে MSS (1460) অনুযায়ী কাটো            → Segment ১, ২, ৩
    প্রতিটিতে TCP header (seq number আলাদা)
L3  প্রতিটি segment-এ IP header                       → Packet ১, ২, ৩
L2  প্রতিটি packet-এ Ethernet header + FCS           → Frame ১, ২, ৩
L1  প্রতিটি frame signal-এ                            → Bits
```

### Segmentation বনাম Fragmentation, আসল পার্থক্য

| | Segmentation | Fragmentation |
|---|---|---|
| Layer | L4 (TCP) | L3 (IP) |
| কেন | Data stream-কে MSS-এ ভাগ | Packet link-এর MTU-র চেয়ে বড় |
| কে করে | Sender-এর TCP | IPv4: sender বা router। IPv6: **শুধু sender** |
| জোড়া লাগায় | Receiver-এর TCP (seq number দিয়ে) | **শুধু final destination-এর IP** |

**বাস্তব সত্য:** আধুনিক TCP **DF=1** রেখে PMTUD ব্যবহার করে, তাই TCP-তে IP fragmentation প্রায় ঘটেই না। Fragmentation মূলত **UDP** (বড় DNS response, VPN), আর **attack**-এ দেখা যায়।

**IPv4 fragment-এর ফিল্ড:** Identification (একই মূল packet-এর টুকরো চেনায়), MF flag (More Fragments), Fragment Offset (৮-byte একক)।
**Fragment attack:** Teardrop (overlapping offset), tiny fragment ও overlapping fragment দিয়ে IDS/firewall evasion (যে security device reassemble না করে পরীক্ষা করে সে ফাঁকিতে পড়ে), fragment flood (reassembly buffer ভরে DoS)।

**Performance নোট:** Real system-এ **TSO/GSO** থাকলে kernel বড় buffer NIC-কে দিয়ে দেয়, আর NIC hardware-এ segment কাটে। তাই Wireshark-এ কখনো 1460-এর চেয়ে বড় "segment" দেখা যায়।

---

## ধাপ ১২: Response ফেরা, TCP-র ভেতরের কাজ

- **ACK:** Server প্রতিটি segment-এর জন্য cumulative ACK পাঠায়। Ack number = "আমি এই byte পর্যন্ত পেয়েছি, এরপরেরটা চাই"। Delayed ACK সাধারণত প্রতি দুই segment-এ একবার।
- **Retransmission:** ACK না এলে RTO timer শেষে আবার পাঠায়। ৩টা duplicate ACK এলে **fast retransmit**।
- **Flow control:** Receiver তার **window size** জানায় (buffer কতটা খালি)। Sender তার বেশি পাঠায় না।
- **Congestion control:** Sender নিজে **cwnd** রাখে। Slow start-এ initial cwnd সাধারণত 10 segment, তারপর বাড়ে। packet loss হলে কমে (CUBIC, BBR)।
- **TCP byte stream:** TCP "message" চেনে না, শুধু ক্রমানুযায়ী byte-স্রোত দেয়। তাই HTTP/TLS নিজেই framing করে (Content-Length, record length)।

**Receiver-এ ওঠার ক্রম:** NIC → interrupt/NAPI → driver → L2 (FCS, EtherType) → L3 (Dst IP, Protocol=6) → L4 (5-tuple দিয়ে socket, seq অনুযায়ী reorder, ACK) → socket receive buffer → ব্রাউজারের `recv()` → TLS decrypt ও tag যাচাই → HTTP parse → HTML render।

---

## ধাপ ১৩: Connection বন্ধ

প্রথমে TLS `close_notify` alert (truncation attack ঠেকাতে)। তারপর TCP:

```
Client → FIN
Server → ACK
Server → FIN
Client → ACK     → Client TIME_WAIT (2×MSL, ~60 সেকেন্ড) → CLOSED
```

TIME_WAIT থাকে যাতে দেরিতে আসা পুরনো packet নতুন connection-কে নষ্ট না করে, আর শেষ ACK হারালে server-এর FIN-এর জবাব দেওয়া যায়। Abnormal বন্ধে **RST**। Server-এ `CLOSE_WAIT`-এ অনেক socket জমা মানে application `close()` করছে না (bug)। TIME_WAIT-এ অনেক জমা মানে অনেক short connection।

## LLC ও MAC: Local নাকি External?

Layer 2 দুই **sublayer**-এ ভাগ:

| Sublayer | Standard | কাজ | কোথায় |
|---|---|---|---|
| **LLC** | IEEE 802.2 | উপরের protocol চেনানো (DSAP/SSAP, SNAP), optional flow/error control | Driver/software |
| **MAC** | 802.3 / 802.11 | MAC address, framing, FCS, medium access (CSMA/CD বা CSMA/CA) | NIC hardware |

**বাস্তবে:** Ethernet II-তে **EtherType** ফিল্ডই LLC-র মূল কাজ (কোন protocol ভেতরে) করে, তাই LLC প্রায় অদৃশ্য। STP-র মতো কিছু protocol এখনো 802.2 LLC ব্যবহার করে।

**Local নাকি external?** দুটোই **শুধু local (hop-by-hop)**, একই link বা LAN-এর ভেতরে। উপরের গল্পে দেখেছো, router পার হলেই পুরনো Ethernet header ফেলে নতুন header বানানো হয়। Server কখনো তোমার laptop-এর MAC দেখে না, দেখে শুধু তার নিজের শেষ hop router-এর MAC।

| Address | Scope | বদলায়? |
|---|---|---|
| MAC (L2) | একটা link/hop | প্রতি hop-এ |
| IP (L3) | End-to-end | NAT ছাড়া শুরু থেকে শেষ একই |
| Port (L4) | Process-to-process | NAT ছাড়া একই |

(VLAN tag, tunnel বা VXLAN-এ L2 কাঠামো জটিল হয়, তবে hop-by-hop নীতি একই।)
