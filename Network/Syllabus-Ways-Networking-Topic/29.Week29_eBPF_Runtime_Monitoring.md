## 1. What is eBPF?

```
eBPF (extended Berkeley Packet Filter) = Technology that allows
running sandboxed programs in the Linux kernel WITHOUT changing
kernel source code or loading kernel modules.

Traditional Monitoring:
  Kernel → /proc, /sys → Userspace tool → Parse → Analyze
  SLOW, incomplete, polling-based

eBPF Monitoring:
  Kernel → eBPF Program (attached to hook point) → Events → Userspace
  FAST, comprehensive, event-driven

eBPF = "JavaScript for the Linux Kernel"
       (safe, sandboxed, dynamically loaded kernel programs)
```

### Why eBPF Matters for Your Research

```
✓ Kernel-level visibility → see EVERYTHING
  - Every packet
  - Every syscall
  - Every process execution
  - Every file access
  - Every network connection

✓ Zero instrumentation
  - No app code changes
  - No sidecar proxies
  - No kernel module loading

✓ High performance
  - JIT compiled to native code
  - Runs at kernel speed
  - Minimal overhead (<1% CPU)

✓ Kubernetes-native
  - Cilium, Falco, Pixie — all eBPF-based
  - Per-pod visibility without pod modification
```

### eBPF Hook Points

```
┌──────────────┬──────────────────────────────────────────────┐
│ Hook         │ Where + Use                                   │
├──────────────┼──────────────────────────────────────────────┤
│ XDP          │ Earliest NIC driver hook                      │
│              │ DDoS mitigation, L4 load balancing            │
│              │ Can DROP before kernel processing (fastest)   │
├──────────────┼──────────────────────────────────────────────┤
│ TC (ingress) │ After XDP, before network stack               │
│ TC (egress)  │ After network stack, before NIC               │
│              │ NetworkPolicy, traffic shaping                │
├──────────────┼──────────────────────────────────────────────┤
│ Socket       │ Per-socket operations (connect, send, recv)   │
│              │ Socket-level policy, per-app monitoring       │
├──────────────┼──────────────────────────────────────────────┤
│ cgroup       │ Per-cgroup (pod) attach                       │
│              │ Pod-level network accounting + policy         │
├──────────────┼──────────────────────────────────────────────┤
│ kprobe       │ Dynamic kernel function tracing               │
│ tracepoint   │ Static kernel tracepoints                     │
│              │ Syscall monitoring (Falco), process tracking  │
├──────────────┼──────────────────────────────────────────────┤
│ LSM          │ Linux Security Module hook (BPF LSM)          │
│              │ Mandatory access control via eBPF             │
└──────────────┴──────────────────────────────────────────────┘
```

## 3. eBPF for Networking

### Cilium eBPF Networking

```
┌──────────────────────────────────────────────────────────────┐
│              eBPF-BASED POD NETWORKING                       │
│                                                              │
│  Pod A (10.244.1.5:45678) → Pod B (10.244.2.8:8080)        │
│                                                              │
│  Step 1: Pod A sends packet                                  │
│       eth0 (veth pair, pod side)                            │
│         │                                                    │
│  Step 2: veth host side → eBPF program (TC ingress)         │
│         - Check: Pod A identity → allowed to send?           │
│         - Check: Pod B identity → allowed to receive?        │
│         - Check: Service DNAT needed? (ClusterIP→Pod IP)     │
│         - Decision: FORWARD / DROP / REDIRECT                │
│         - Record: Flow event → Hubble                        │
│         │                                                    │
│  Step 3: Route to destination pod (same node or cross-node)  │
│                                                              │
│  ALL THIS in eBPF — no iptables, no kube-proxy!             │
└──────────────────────────────────────────────────────────────┘
```

### Performance Comparison

```
Operation            iptables       eBPF
────────────────────────────────────────────
Packet lookup        O(n) rules     O(1) hash table
Service DNAT         ~50K rules at  O(1) map lookup
                      1000 services
Policy check         Linear chains  Direct map lookup
Connection tracking  conntrack      eBPF CT (or reuse)
Rule update          Full table     Atomic map update
                     rewrite (slow)
Observability        None built-in   Per-packet events
```

## 4. eBPF for Security

### Runtime Threat Detection

```
eBPF Security Monitoring Points:

1. Process Execution (kprobe: execve)
   → What processes are running in containers?
   → Detect: shells, nmap, crypto miners

2. File Access (kprobe: open, write)
   → Sensitive file access (/etc/shadow, /etc/kubernetes)
   → Detect: credential theft

3. Network Connection (kprobe: tcp_connect, cgroup)
   → Outbound connections from pods
   → Detect: C2 communication, data exfiltration

4. Privilege Operations (kprobe: setuid, cap_capable)
   → Privilege escalation attempts
   → Detect: container escape

5. Syscall Patterns (tracepoint: raw_syscalls)
   → Sequence of syscalls per process
   → Detect: anomalous behavior via ML on syscall sequences
```

### Falco + eBPF

```
Falco uses eBPF probe (modern) instead of kernel module (legacy):

  eBPF probe → attaches to syscall tracepoints
  → Captures: execve, open, connect, setuid, ...
  → Filtered by Falco rules
  → Alert: "Unexpected behavior detected!"

Research Integration:
  Falco eBPF probe → syscall event stream
  → Extract: process tree, file access pattern, network connections
  → Feature: "execve_count_per_min", "unique_ports_accessed"
  → ML: baseline per-container behavior → detect deviations
```

### Tools Using eBPF

```
┌────────────────┬──────────────────────────────────────────────┐
│ Cilium         │ CNI + NetworkPolicy + Hubble (observability) │
│ Falco          │ Runtime security (syscall monitoring)        │

For Research: Cilium + Hubble + Tetragon = Complete eBPF stack
```

### Research: eBPF as Dataset Source

```
eBPF gives you:

1. Network Telemetry (Hubble):
   Every flow, with identity, verdict, L7 info
   → Primary dataset source

2. Process Telemetry (Tetragon):
   Process execution, capabilities, privilege changes
   → Correlate with network events

3. File Access Telemetry (Falco):
   Sensitive file access patterns
   → Credential theft features

4. Syscall Telemetry:
   Raw syscall sequences
   → Deep behavioral ML models

Your Research Pipeline:
  eBPF (kernel) → Cilium/Hubble/Falco → Structured Events
  → Kafka → Feature Extraction → ML Model → SHAP → Explanation
```
