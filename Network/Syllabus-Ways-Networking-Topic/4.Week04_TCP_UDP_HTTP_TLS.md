## 1. TCP (Transmission Control Protocol)

### সংজ্ঞা
TCP হলো **connection-oriented, reliable** transport layer protocol. প্রতিটি byte-র delivery guarantee করে, ক্রম ঠিক রাখে, error থাকলে retransmit করে।

```
TCP Characteristics:
  ✓ Connection-oriented  (connection establish করে, তারপর data)
  ✓ Reliable             (acknowledgment + retransmission)
  ✓ Ordered              (sequence number দিয়ে ক্রম ঠিক রাখে)
  ✓ Error-checked        (checksum)
  ✓ Flow control         (receiver-কে overwhelm করে না)
  ✓ Congestion control   (network-কে overwhelm করে না)
  ✓ Full-duplex          (দুই দিকেই data চলতে পারে)
```

### TCP Header Structure

```
┌────────────────────────────────────────────────────────────────┐
│ 0                   8                   16              24  31 │
├────┬────┬────┬────┬────┬────┬────┬────┬────┬────┬────┬────┬────┤
│        Source Port            │       Destination Port         │
├────┼────┼────┼────┼────┼────┼────┼────┼────┼────┼────┼────┼────┤
│                        Sequence Number                         │
├────┼────┼────┼────┼────┼────┼────┼────┼────┼────┼────┼────┼────┤
│                     Acknowledgment Number                      │
├────┼────┼────┼────┼────┼────┼────┼────┼────┼────┼────┼────┼────┤
│ Data  │ Res │ ECN │U│A│P│R│S│F│                               │
│Offset │ rvd │ NS  │R│C│S│S│Y│I│         Window Size            │
│       │     │  C  │G│K│H│T│N│N│                               │
├────┼────┼────┼────┼────┼────┼────┼────┼────┼────┼────┼────┼────┤
│       Checksum                │      Urgent Pointer            │
├────┼────┼────┼────┼────┼────┼────┼────┼────┼────┼────┼────┼────┤
│                    Options (if Data Offset > 5)                 │
└────────────────────────────────────────────────────────────────┘

Key Fields:
  Source Port:      16-bit — sender-এর port
  Destination Port: 16-bit — receiver-এর port
  Sequence Number:  32-bit — byte-level numbering for ordering
  ACK Number:       32-bit — next expected byte
  Data Offset:      4-bit — TCP header length (in 32-bit words)
  Flags:            9 bits — URG, ACK, PSH, RST, SYN, FIN (+ NS, CWR, ECE)
  Window Size:      16-bit — flow control (receiver buffer space)
  Checksum:         16-bit — error detection
```

### TCP Connection Lifecycle

```
                    CLIENT                         SERVER
                      │                              │
    [CLOSED]          │                              │      [LISTEN]
                      │                              │
                      │─────────── SYN ────────────►│
                      │                              │
    [SYN-SENT]        │◄─────── SYN + ACK ──────────│      [SYN-RECEIVED]
                      │                              │
                      │─────────── ACK ────────────►│
                      │                              │
    [ESTABLISHED]     │◄════════ DATA ════════════►│      [ESTABLISHED]
                      │                              │
         ... Data transfer phase ...                 │
                      │                              │
    [FIN-WAIT-1]      │─────────── FIN ────────────►│
                      │                              │      [CLOSE-WAIT]
    [FIN-WAIT-2]      │◄─────────── ACK ────────────│
                      │                              │
    [TIME-WAIT]       │◄─────────── FIN ────────────│      [LAST-ACK]
                      │                              │
                      │─────────── ACK ────────────►│
    [CLOSED]          │                              │      [CLOSED]
                      │                              │
    TIME-WAIT = 2×MSL (typically 60 sec)
```

## 2. UDP (User Datagram Protocol)

### সংজ্ঞা
UDP হলো **connectionless, unreliable** transport layer protocol — fast কিন্তু delivery guarantee নেই।

```
UDP Characteristics:
  ✗ Connectionless       (connect না করেই send)
  ✗ Unreliable           (acknowledgment নেই)
  ✗ No ordering          (sequence number নেই)
  ✗ No flow control      (send করে দেয়, receiver handle করুক)
  ✗ No retransmission    (packet lost = data lost)
  ✓ Fast + Low overhead  (8 byte header only)
  ✓ Multicast/Broadcast support
```

### UDP Header (Simple!)

```
┌──────────────────────────────────────────┐
│ 0          16           31               │
├──────────┬──────────┬──────────┬─────────┤
│ Src Port │ Dst Port │ Length   │ Checksum│
│ (16 bit) │ (16 bit) │ (16 bit) │ (16 bit)│
└──────────┴──────────┴──────────┴─────────┘
│                 DATA                      │
└───────────────────────────────────────────┘

Header size: 8 bytes (fixed) vs TCP: 20-60 bytes
```

### TCP vs UDP

```
Feature             TCP                     UDP
────────────────────────────────────────────────────
Connection          Yes (SYN-SYN/ACK-ACK)  No
Reliability         Guaranteed              Not guaranteed
Ordering            Maintained              Not maintained
Header Size         20-60 bytes             8 bytes
Speed               Slower                  Faster
Flow Control        Yes                     No
Congestion Control  Yes                     No
Use Cases           Web, Email, File        Video, VoIP, DNS, Gaming
Kubernetes          kube-apiserver (6443)   CoreDNS (53), VXLAN tunnel
```

### UDP Use Cases

```
DNS:        Query small, fast needed — UDP perfect (TCP for large responses)
VoIP:       Real-time audio — packet loss tolerable, delay unacceptable
Video stream:  Buffer handles occasional loss, speed critical
Gaming:     Position updates — stale data useless, latest matters
VXLAN:      Kubernetes overlay networking-এ UDP tunnel use হয়
```

### Research Context
- TCP vs UDP traffic ratio → network profiling feature
- UDP-based DDoS (amplification attack: DNS, NTP)
- Kubernetes VXLAN overlay → UDP encapsulated traffic analysis
- Dataset labeling: TCP flow vs UDP flow → different behavior patterns

## 3. Three-way Handshake

### সংজ্ঞা
TCP connection establish করার 3-step process, যেখানে client ও server synchronization করে — sequence numbers exchange করে।

```
Step 1: Client → Server  [SYN]
        SYN flag set, Seq = X (random initial sequence number)

Step 2: Server → Client  [SYN + ACK]
        SYN flag set, ACK flag set
        Seq = Y (server's random ISN)
        ACK = X + 1 ("তোমার SYN পেয়েছি, next byte X+1 চাই")

Step 3: Client → Server  [ACK]
        ACK flag set
        Seq = X + 1
        ACK = Y + 1 ("তোমার SYN/ACK পেয়েছি, next byte Y+1 চাই")

CONNECTION ESTABLISHED ✓
```

### Visual (Wireshark-Style)

```
No.  Time     Source         Dest           Protocol  Info
─────────────────────────────────────────────────────────────
1    0.000    192.168.1.5    93.184.216.34  TCP      52341→80 [SYN] Seq=0
2    0.015    93.184.216.34  192.168.1.5    TCP      80→52341 [SYN,ACK] Seq=0 Ack=1
3    0.016    192.168.1.5    93.184.216.34  TCP      52341→80 [ACK] Seq=1 Ack=1
```

### Initial Sequence Number (ISN)

```
ISN randomly generate করা হয় (security purpose).
Predictable ISN = TCP sequence prediction attack possible.

Client ISN: X (e.g., 3847291034)
Server ISN: Y (e.g., 2194385721)

Handshake-এর পর:
  Client next Seq = X + 1
  Server next Seq = Y + 1
```

### SYN Flood Attack (Research Relevant!)

```
Normal:   Client ──SYN──► Server (Server allocates resources)
          Client ◄─SYN/ACK── Server
          Client ──ACK──► Server → ESTABLISHED

Attack:   Attacker ──SYN──► Server (spoofed IP)
          Server allocates resources → SYN-RECEIVED state
          Server ◄─SYN/ACK── (কখনো ACK আসে না)
          Server waits... timeout... resource waste

          Attacker sends THOUSANDS of SYN → Server SYN queue full
          → Legitimate clients can't connect = DoS
```

### Research Context
- SYN flood → DDoS detection-এর primary use case
- Connection establishment rate feature → anomaly baseline
- Wireshark-এ handshake analyze করে RTT, retransmission, connection success rate মাপা

## 4. TCP Flags

### সংজ্ঞা
TCP header-র 9টি control bits যা connection state এবং segment purpose control করে।

### Flag Details

```
┌──────┬─────┬──────────────────────────────────────────────────┐
│ Flag │ Bit │ Purpose                                          │
├──────┼─────┼──────────────────────────────────────────────────┤
│ SYN  │  S  │ Synchronize — connection initiate                │
│ ACK  │  A  │ Acknowledge — previous data received            │
│ FIN  │  F  │ Finish — connection gracefully close             │
│ RST  │  R  │ Reset — connection abruptly abort                │
│ PSH  │  P  │ Push — data immediately deliver to application   │
│ URG  │  U  │ Urgent — urgent pointer valid (rarely used)      │
│ CWR  │  C  │ Congestion Window Reduced — congestion signal    │
│ ECE  │  E  │ ECN Echo — Explicit Congestion Notification      │
│ NS   │  N  │ Nonce Sum — ECN protection (experimental)        │
└──────┴─────┴──────────────────────────────────────────────────┘
```

### Common Flag Combinations

```
SYN              : Connection initiation (handshake step 1)
SYN+ACK          : Connection acknowledgment (handshake step 2)
ACK              : Normal data transfer acknowledgment
FIN+ACK          : Connection termination
FIN+PSH+ACK      : Final data push + close
RST              : Connection refused / abort
RST+ACK          : Acknowledged reset
PSH+ACK          : Data push with acknowledgment
```

### Flag Analysis (Attack Detection)

```
Normal flow:    SYN → SYN/ACK → ACK → [DATA: PSH+ACK, ACK] → FIN/ACK → FIN/ACK → ACK

Abnormal patterns:
  - SYN only (no follow-up ACK)      → SYN flood / scan
  - RST after SYN                    → Port closed
  - RST during data transfer         → Connection hijack attempt
  - FIN without SYN                  → Orphaned/broken connection
  - All flags = 0                    → NULL scan (Nmap evasion)
  - FIN+PSH+URG (Xmas scan)         → Nmap OS detection
```

### Research Context — IMPORTANT
- TCP flag combination → critical ML feature
- Nmap scan detection → unusual flag patterns
- Dataset column: `tcp_flags` → binary/one-hot encoded feature
- Real-time flag anomaly → IDS rule trigger

## 5. Flow Control

### সংজ্ঞা
Flow control TCP-র mechanism যা নিশ্চিত করে যে **sender, receiver-এর চেয়ে fast data পাঠাবে না**। Receiver-এর buffer overflow prevent করে।

### Sliding Window Protocol

```
Receiver advertises: "Window Size = 4096 bytes" (buffer space available)

Sender can send up to 4096 bytes WITHOUT waiting for ACK.

┌─────────────────────────────────────────────────────┐
│                Sender Window (4096 bytes)            │
│  ┌──────┬──────┬──────┬──────┬──────┬──────┬──────┐ │
│  │ Byte │ Byte │ Byte │ Byte │ Byte │ Byte │ Byte │ │
│  │  1   │  2   │  3   │  4   │  5   │  6   │  7   │ │
│  │ Sent │ Sent │ Sent │ Can  │ Can  │ Can  │ Can  │ │
│  │&ACKed│&ACKed│&ACKed│ Send │ Send │ Send │ Send │ │
│  └──────┴──────┴──────┴──────┴──────┴──────┴──────┘ │
│    └── Window moved ──►│◄─── Usable Window ──────► │
└─────────────────────────────────────────────────────┘
```

### Window Size Dynamics

```
Time 1: Receiver window = 8192 bytes
        → Sender sends 8192 bytes (4 segments of 2048 bytes each)

Time 2: Receiver processes 4096 bytes, buffer frees up
        → Sends ACK with Window = 4096 + 4096 = 8192 (sliding forward)

Time 3: Receiver busy, buffer full (app slow to read)
        → Sends ACK with Window = 0  ◄── PAUSE SENDING!

Time 4: Sender sends "Window Probe" (1 byte) periodically
        → Receiver: Window = 4096  ◄── RESUME!

Time 5: Receiver: Window = 2048 (buffer filling up again)
        → Sender slows down
```

### Zero Window Condition

```
Problem: Receiver application slow → buffer full → Window = 0
         Sender stops → idle timeout risk

Solution: TCP Persist Timer → sender periodically sends
          1-byte "window probe" to check if receiver ready

Research: Zero window events → network/application bottleneck indicator
```

### Research Context
- Flow control behavior → application performance indicator
- Zero window events → potential DoS or app bottleneck
- Window size as dataset feature → traffic pattern analysis
- Kubernetes pod communication-এ flow control issues → CNI tuning

## 6. Retransmission

### সংজ্ঞা
TCP reliable delivery-র core mechanism — packet lost বা corrupt হলে **automatic retransmission**।

### Retransmission Triggers

#### 1. Timeout-based (RTO - Retransmission Timeout)

```
Sender: Pkt 1-10 পাঠালাম
        Timer start (RTO = Smoothed RTT + 4×RTT Variance)

Case A: ACK আসে RTO-র আগে → Timer reset → Normal ✓
Case B: RTO expire, ACK আসেনি → Retransmit oldest unacknowledged segment
        → RTO double (Exponential Backoff)
```

#### 2. Duplicate ACK-based (Fast Retransmit)

```
Sender: Seq=1, Seq=101, Seq=201, Seq=301, Seq=401
        (5 segments পাঠালাম, প্রতিটি 100 bytes)

Case: Seq=201 lost, Seq=301 এবং 401 arrive out-of-order

Receiver: 
  Gets Seq=101 → ACK=201 
  Gets Seq=301 → ACK=201 (duplicate! expecting 201)
  Gets Seq=401 → ACK=201 (2nd duplicate!)

** 3 Duplicate ACKs = Fast Retransmit trigger **
  → Immediately retransmit Seq=201, don't wait for RTO
```

### Retransmission Visual

```
Sender                               Receiver
  │                                     │
  │── Seq=1:100 ──────────────────────►│ ✓ Received
  │◄────────────── ACK=101 ────────────│
  │                                     │
  │── Seq=101:200 ───────────────────►│ ✗ LOST!
  │── Seq=201:300 ───────────────────►│ ✓ (out of order)
  │── Seq=301:400 ───────────────────►│ ✓ (out of order)
  │                                     │
  │◄────────────── ACK=101 ────────────│ (duplicate #1)
  │◄────────────── ACK=101 ────────────│ (duplicate #2)
  │◄────────────── ACK=101 ────────────│ (duplicate #3)
  │                                     │
  │── Seq=101:200 ───────────────────►│ ✓ (Fast Retransmit!)
  │                                     │
  │◄────────────── ACK=401 ────────────│ (cumulative ACK)
```

### Research Context — CRITICAL
- **Retransmission count** → KEY ML feature for network health
- High retransmission → congestion, faulty link, or attack
- Retransmission rate = retransmit packets / total packets
- Kubernetes pod network reliability metric
- TCP retransmission pattern → ML anomaly detection

## 7. HTTP

### সংজ্ঞা
HTTP (HyperText Transfer Protocol) হলো L7 **request-response** protocol — web-এর foundation।

```
Client (Browser)                        Server (Nginx/Apache)
     │                                        │
     │── GET /index.html HTTP/1.1 ──────────►│
     │   Host: example.com                    │
     │                                        │
     │◄── HTTP/1.1 200 OK ──────────────────│
     │   Content-Type: text/html              │
     │   Content-Length: 1234                 │
     │                                        │
     │   <html><body>...</body></html>        │
```

### HTTP Request Structure

```
┌────────────────────────────────────────┐
│ Request Line                           │
│ GET /api/users HTTP/1.1                │
├────────────────────────────────────────┤
│ Headers                                │
│ Host: example.com                      │
│ User-Agent: Mozilla/5.0                │
│ Accept: application/json               │
│ Content-Type: application/json         │
│ Authorization: Bearer token123         │
│ Cookie: session=abc123                 │
├────────────────────────────────────────┤
│ Empty Line (CRLF)                      │
├────────────────────────────────────────┤
│ Body (POST/PUT-এই থাকে, GET-এ থাকে না) │
│ {"name": "Ash", "email": "a@b.com"}    │
└────────────────────────────────────────┘
```

### HTTP Methods

```
GET     : Resource retrieve
POST    : Resource create
PUT     : Resource update/replace
PATCH   : Resource partial update
DELETE  : Resource remove
HEAD    : GET without body (headers only)
OPTIONS : Supported methods query
TRACE   : Debug (echo request — security risk!)
```

### HTTP Status Codes

```
1xx: Informational
2xx: Success
  200 OK            - Request successful
  201 Created       - Resource created
  204 No Content    - Success, no body

3xx: Redirection
  301 Moved Permanently
  302 Found (Temporary)
  304 Not Modified

4xx: Client Error
  400 Bad Request
  401 Unauthorized
  403 Forbidden
  404 Not Found
  429 Too Many Requests

5xx: Server Error
  500 Internal Server Error
  502 Bad Gateway
  503 Service Unavailable
  504 Gateway Timeout
```

### HTTP/1.1 vs HTTP/2 vs HTTP/3

```
HTTP/1.1:  One request per TCP connection (head-of-line blocking)
           Keep-Alive → connection reuse

HTTP/2:    Multiplexing (multiple streams এক TCP connection-এ)
           Header compression (HPACK)
           Server Push

HTTP/3:    Uses QUIC (UDP-based), not TCP
           Built-in TLS 1.3
           0-RTT connection
           No head-of-line blocking (per-stream)
```

### Research Context
- HTTP method distribution → feature (normal: GET > POST > others)
- HTTP status code sequence → attack pattern (e.g., 404 storm = scan)
- HTTP header analysis → user-agent anomalies, malicious headers
- Kubernetes: kube-apiserver uses HTTP/HTTPS, microservices use REST/gRPC

## 8. HTTPS

### সংজ্ঞা
HTTPS = HTTP + TLS (Transport Layer Security). HTTP data encrypted channel-এর মাধ্যমে যায়।

```
HTTP:   [Plain Text Request] ───► Internet (visible to anyone!) ───► Server
        ⚠ MAN-IN-THE-MIDDLE দেখতে পায় সবকিছু

HTTPS:  [Encrypted Request] ───► Internet (gibberish to eavesdropper) ───► Server
        ✓ Only client & server can read
```

### HTTPS Components

```
HTTPS = HTTP over TLS = HTTP + Encryption + Authentication + Integrity

1. Encryption:      Data encrypted — eavesdropper কিছুই বুঝবে না
2. Authentication:   Certificate verify করে — "আসলেই example.com-এর সাথে কথা বলছি?"
3. Integrity:        Data tamper-proof — মাঝখানে কেউ modify করতে পারবে না
```

### TLS Position in Stack

```
┌──────────────────────────┐
│   HTTP (Application)      │  ← Plain data
├──────────────────────────┤
│   TLS (Session Layer-ish) │  ← Encryption/Decryption
├──────────────────────────┤
│   TCP (Transport)         │  ← Reliable delivery
├──────────────────────────┤
│   IP (Network)            │  ← Routing
├──────────────────────────┤
│   Ethernet (Data Link)    │  ← Physical delivery
└──────────────────────────┘
```

### Research Context
- TLS encryption → traffic analysis blind
- However: **TLS handshake, SNI, certificate metadata** এখনও visible
- Encrypted Traffic Analysis (ETA) → ML model encrypted traffic থেকে pattern detect করে
- Kubernetes: all internal API communication is HTTPS (TLS)

## 9. TLS

### সংজ্ঞা
TLS (Transport Layer Security) cryptographic protocol যা network communication secure করে — encryption, authentication, integrity।

### TLS Handshake (1.2 — Full)

```
Client                                  Server
  │                                       │
  │── (1) ClientHello ──────────────────►│
  │   TLS version, cipher suites,         │
  │   random number, SNI (server name)    │
  │                                       │
  │◄── (2) ServerHello ──────────────────│
  │   Selected cipher, random number,     │
  │   session ID                          │
  │                                       │
  │◄── (3) Certificate ─────────────────│
  │   Server's public key + certificate   │
  │   chain to trusted CA                 │
  │                                       │
  │◄── (4) ServerHelloDone ─────────────│
  │                                       │
  │── (5) ClientKeyExchange ───────────►│
  │   Pre-master secret (RSA) or          │
  │   DH key parameters (DH)              │
  │                                       │
  │── (6) ChangeCipherSpec ────────────►│
  │── (7) Finished (encrypted) ────────►│
  │                                       │
  │◄── (8) ChangeCipherSpec ────────────│
  │◄── (9) Finished (encrypted) ────────│
  │                                       │
  │◄══════ ENCRYPTED DATA ═══════════►│
```

### TLS 1.3 — Simplified Handshake (Faster!)

```
Client                                  Server
  │                                       │
  │── (1) ClientHello ──────────────────►│
  │   Supported ciphers + Key Share (DH)  │
  │                                       │
  │◄── (2) ServerHello ──────────────────│
  │   Chosen cipher + Key Share +         │
  │   Certificate + Finished              │
  │                                       │
  │── (3) Finished ─────────────────────►│
  │                                       │
  │◄══════ ENCRYPTED DATA ═══════════►│
  │                                       │
  │ TLS 1.3 = 1-RTT (vs 2-RTT in TLS 1.2)│
  │ 0-RTT mode: previous session resume → │
  │  even faster! (but replay risk)        │
```

### TLS Certificate Chain

```
Root CA (trusted by OS/Browser)
  │
  ├── Intermediate CA 1
  │     │
  │     └── Intermediate CA 2
  │           │
  │           └── Server Certificate (example.com)
  │
  Verification: Browser traces chain up to trusted Root CA
  → All signatures valid → Certificate trusted ✓
```

### Key TLS Fields (Research Features)

```
TLS Version:        1.2 vs 1.3
Cipher Suite:       TLS_AES_128_GCM_SHA256
SNI (Server Name Indication):  example.com (visible in plaintext!)
Certificate Validity:  Not Before / Not After
Certificate Issuer:    Let's Encrypt / DigiCert
Certificate Subject:   CN=example.com
Public Key Type:       RSA 2048 / ECDSA P-256
JA3/JA4 Fingerprint:   TLS client fingerprint (ML feature!)
```

### Research Context — VERY IMPORTANT

```
1. JA3/JA4 Fingerprinting:
   TLS ClientHello-এর fields (version, cipher, extensions) থেকে
   fingerprint generate করা হয় → malware/tool identification
   → CRITICAL feature for ML-based attack detection

2. Encrypted Traffic Analysis (ETA):
   TLS এ data encrypt হয়ে যায়, কিন্তু:
   - Packet size sequence
   - Inter-arrival time
   - TLS handshake metadata
   → ML model attack traffic identify করতে পারে WITHOUT decryption!

3. mTLS (Mutual TLS):
   Kubernetes service mesh (Istio)-এর backbone
   Client + Server উভয়ই certificate present করে
   → Zero-trust networking

4. TLS-based Attacks:
   - Expired/self-signed certificate usage
   - Weak cipher negotiation
   - TLS downgrade attack
   - TLS stripping (HTTPS → HTTP)
   - Certificate spoofing

5. Dataset Features from TLS:
   - JA3 fingerprint
   - TLS version
```
